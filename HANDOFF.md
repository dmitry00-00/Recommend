# Transformative Media — пакет handoff

Каркас фронтенда, собранный **из** дизайн-системы, а не по её мотивам: токены, шрифты,
стили компонентов, моки и словари строк выгружены из системы программно. Значения здесь
не набраны руками — поменяется токен, файл перегенерируется.

## Посмотреть сразу, без установки

Откройте **`dist/standalone.html`** — двойным щелчком, из файла. Внутри одного файла
лежит всё: скрипт, стили и шрифты. Это собранный экран «Сегодня» на слое данных: силы,
склейка, кадры, скелетоны загрузки при переключении сил.

Корневой `index.html` так не открывается и не должен: это точка входа Vite, в нём ссылка
на `src/main.tsx`, а TSX браузер сам не исполняет. Если открыть его напрямую, он это и скажет.

Пересобрать самодостаточную страницу после правок: `npm run build:standalone`.

## Запуск с исходников

```bash
npm install
npm run dev        # http://localhost:5173
npm run typecheck  # tsc --noEmit, без ошибок
npm run build      # tsc -b && vite build
```

Тема переключается атрибутом на `<html>`: `data-theme="dark"` — «Лента» (основная),
`data-theme="light"` — «Просмотровая». В `index.html` стоит `dark`.

## Telegram Mini App

Основная среда — мини-приложение внутри Telegram; бот — **`@recomend_media_bot`**
(константа `BOT_USERNAME` в `src/lib/telegram.ts`, для ссылок-приглашений и «поделиться»).
Правила оболочки лежат в разделе «Telegram Mini App» дизайн-системы, здесь — что это значит для кода:

- `AppShell` в варианте `telegram` не рисует свою шапку: её рисует мессенджер;
- `colorScheme` из Telegram переключает `data-theme` (`dark` → «Лента», `light` → «Просмотровая»),
  палитра `themeParams` при этом **не** подмешивается: иначе от направления ничего не остаётся;
- нижняя навигация уже поднята над домашним индикатором через `--tm-safe-bottom`;
- `HashRouter` совместим с мини-приложением: адресной строки там нет, состояние живёт в хеше;
- внешние ссылки (`DiscussionLink`, `ExternalAnalysisLink`) открываются средствами Telegram —
  внутренние в мессенджере, внешние в браузере.

Что из этого в коде (19.09):

| Где | Что |
|---|---|
| `index.html` | `telegram-web-app.js` в `<head>`, `viewport-fit=cover`; фон `body` — из токена, не инлайном |
| `src/lib/telegram.ts` | типизированный слой над `window.Telegram.WebApp`: `initTelegram()` (тема → `data-theme`, зоны `safeAreaInset` + `contentSafeAreaInset` → `--tm-safe-top/bottom`, `viewportStableHeight` → `--tm-viewport-height`, `expand`, `disableVerticalSwipes`, `ready`), `openExternal(url)` (t.me/tg:// → `openTelegramLink`, остальное → `openLink`), `showBackButton()`. Вне Telegram — всё no-op |
| `src/components/AppShell.tsx` | оболочка: вариант выбирается по среде; `NavLink` даёт `tm-nav__item--on`; на вложенных экранах — кнопка «Назад» в шапке мессенджера |
| `src/styles/app.css` | раскладка приложения поверх превью-рамки системы: оболочка в высоту экрана, листается `main`, а не документ; в Telegram — без рамки и без `max-width` |
| `tools/inline-dist.cjs` | внешние скрипты не инлайнятся — `standalone.html` по-прежнему открывается из файла |

Два решения, которых в правилах системы нет:

- шапку и подложку мессенджера красим в **наши** `surface-100` / `surface-card`
  (`setHeaderColor`, `setBackgroundColor`, `setBottomBarColor`) — направление обратное
  запрещённому: не палитра Telegram в приложение, а поверхность приложения на хром Telegram;
- зоны берутся из событий SDK, а не из `env(safe-area-inset-*)`: внутри WebView `env()`
  часто отдаёт нули; `env()` остаётся фолбэком для клиентов без Bot API 8.0.

Telegram принимает цвета только как `#rrggbb`; минификатор сжимает `#ffffff` до `#fff`,
поэтому `readToken` в `lib/telegram.ts` разворачивает короткую запись — не убирать.

## Правила, которые нельзя нарушить при переносе

1. **Значения только из токенов.** В компонентах нет ни одного «магического» кегля, цвета
   или отступа: всё через `var(--tm-*)` и классы `.tm-*`. Типографика компонентов
   сгенерирована из токенов — если нужен другой размер, он появляется в системе, а не в CSS экрана.
2. **Бизнес-логики на фронте нет.** Уровень усилия, готовность, спойлерность, тексты
   объяснений и причины перестроений приходят из данных. Экран может только выбрать и
   разложить — как `previousFrame()` в `TodayScreen`: это поиск последнего пройденного шага,
   а не вычисление рекомендации.
3. **Строки — в `i18n`, не в разметке.** Одно действие называется одинаково по всему сценарию.
4. **Числа — только при `showDetails`.** Пропс есть у `OperationChip`, `RecommendationCard`
   и карты; без него уровень называется словами.
5. **Кадры лежат встык.** `margin-top: -1px` у соседних `.tm-rec` — это не хак, а метафора
   ленты: рамки сливаются в одну линию перфорации. Зазор между кадрами ломает направление.

## Экран «Произведение» (19.09)

Страницы-витрины `ScreenWork` в этой папке нет — есть только бандл компонентов. Раскладка
собрана по порядку разбора из `CheckInFlow` (приёмы → разборы авторов → где говорили) и по
контракту `WorkDetail` §16; при сверке с витриной в системе править `WorkScreen.tsx` и
раздел «Экран „Произведение“» в `src/styles/app.css` — там только отступы, типографика
разделов через классы системы (`tm-title-3`, `tm-label`, `tm-work-sm`, `tm-caption`).

Что экран берёт из данных и как:

- **закончено ли** — по дневнику: есть запись с этим произведением в статусе `finished`;
- **что можно открывать** — `spoilerLevel` из настроек; после завершения открыто всё;
- приёмы с уровнем выше допустимого лежат под `SpoilerGuard`, остальные — открыто;
- разборы получают `spoilerLevel` и сами закрываются; места разговора закрыты до
  завершения, если у них `spoilers: true`;
- готовность — `ReadinessNotice` по `prerequisites` c `met: false` (готовность не считается,
  только выбирается из пришедшего списка);
- `getWork` теперь возвращает `WorkDetail | undefined`; для неизвестного id — экран «нет такого».

**Желания и заряд (19.09).** Раздел «Кто чего хочет»: явное желание видно всегда, подавленное —
по тому же правилу спойлеров, что приёмы (уровень выше допустимого → под `SpoilerGuard`);
рядом словами — насколько оно читаемо (`visibility`). `desireModel: 'none' | 'diffuse'` даёт
фразу о форме («героя с ясной целью здесь нет — это форма, а не недостаток»). У приёма —
метка ценностного заряда (`charge`): четвёртая позиция «отрицание отрицания» нарисована
двойной рамкой цвета метки, чтобы не путать с открытым «обманом ожидания». Стили
`.tm-trope__charge` и `.tm-desires` живут в `app.css` до появления в дизайн-системе.

«В планы» на этой странице пока без эндпоинта (в §17 есть только отзыв на рекомендацию) —
состояние живёт на экране; «Начать» вызывает `startWork` и ведёт в дневник.

## Экран «Карта» (19.09)

`CognitiveMap` переписан на d3, как просил PORTING.md, но только на `d3-shape` и `d3-scale`
(`lineRadial`, `curveLinearClosed`, `pointRadial`, `scaleLinear`): полный d3 в бандл не тянем.
Разметка — SVG с классами системы, геометрия — в компоненте; смысловых вычислений нет.
Пакеты добавлены в `package.json` вместе с типами.

Витрины `ScreenMap` здесь нет — экран собран из перечисленных для него частей (`CognitiveMap`,
`TimeScrubber`, `UncertaintyMark`) и строк, которые уже лежали в словаре (`makeFocus`, `roughMap`).
Решения, которые стоит сверить с системой:

- **ось времени и карта связаны**: выбранная точка истории перерисовывает карту. Последняя точка
  истории считается текущим состоянием (состояние меняется только через причину, а каждая
  причина — точка истории). Для более ранних точек уровень и диапазон — из истории, уверенность
  — текущая: в `StateHistoryPoint` её нет, а она влияет только на мягкость линии. В моке даты
  `state.asOf` (17.09) и последней точки (14.09) расходятся — это артефакт мока;
- **выбор операции** на карте (`onSelect`) открывает под ней карточку: чип, строка операции,
  `UncertaintyMark` с числами при «подробностях», тренд словами, сколько пройдено с этой
  операцией, «Сделать фокусом»;
- **фокус** — `targets` + `suggestedTargets` из данных; «Сделать фокусом» пока меняет только
  состояние экрана: эндпоинта для целей развития в §17 нет;
- переключатель «Списком» — режим `list` карты (таблица); в режиме поля таблица остаётся для
  скринридера (`tm-sr`), как в бандле.

## Оболочка и системное (21.09)

используются.

## Подбор на собственных данных участника (22.09)

Первый рабочий контур модели — без бэкенда, на моках, чтобы проверять подбор на живой истории:

- **Разметка истории** — `src/mocks/userAnnotations.ts`: 93 фильма участника размечены
  первично (provider `anthropic_api`, модель claude-opus-5, статус `needs_review`) — операции
  с интенсивностью, уровень 1–10, барьеры, предупреждения, нишевый шедевр, уверенность, строка
  «что делает». Разметка по знанию фильмов, без просмотра: это кандидаты для кураторской.
  `api.history()` подкладывает её в карточки, у которых операций нет.
- **Оценки участника** — `src/mocks/userRatings.ts`, генерируется без сети
  `tools/build-user-ratings.mts <файлы экспорта>` (88 оценок, 1–5). Это вес наблюдения для
  модели; `getJourney` их вырезает — в интерфейс оценки не попадают (правило 4).
- **Состояние из истории** — `src/lib/model/deriveState.ts`: по каждой операции — взвешенный
  70-й квантиль нагрузки (`уровень × (0.6 + 0.4 × интенсивность)`) по досмотренному, где вес —
  оценка; диапазон и уверенность — от числа наблюдений; тренд — последний год против остального;
  комфортный уровень и медиаграмотность — из того же. `deriveMap` строит историю точками по
  кварталам и следы. `getMap` и `getSlate` берут это, когда история размечена; иначе — моки.
  Эвристика этапа 1 — IRT и Брэдли–Терри по ROADMAP §5 (этап 4).
- **Пул кандидатов** — `src/mocks/candidates.ts` (30 фильмов, которых нет в истории: половина
  рядом со вкусом, половина — шаг в сторону и вверх; разметка того же вида) +
  `src/mocks/candidateMedia.ts` (генератор `tools/build-candidate-media.mts`: TMDb-поиск по
  названию и году → ID, кадр, описание, кинотеатры; Кинопоиск поверх, пока есть лимит) +
  каталог моков с объяснениями. Просмотренное отсеивается по внешним ID.
- **Подбор** — `src/lib/model/recommend.ts`: цель по уровню = комфорт + шаг по усилию
  (−1.2 / +0.4 / +1.4), оценка = близость уровня × 0.55 + совпадение операций × 0.45 (нагрузка
  чуть выше уровня участника — лучше всего) ± нишевость; слот — `stretch` при +1.5 и выше,
  `side_step` при барьерах формы, иначе `next_step`; в слейте не больше двух с одной ведущей
  операцией. Объяснение: «что делает» — из разметки; «почему вам» — из операции, ради которой
  выбран кадр, с честной формулировкой (сильная сторона / чуть больше обычного / в вашем темпе).

Проверка без браузера — скрипт вроде `scratchpad/model-test.mts`: состояние, слейты по трём
усилиям с оценками. Сейчас у участника комфорт 5.0, операции 4–5.3 (кроме «целого» — мало
данных); «обычный» слейт: Платформа, Исчезновение, Воспоминания об убийстве, Временная петля,
Зодиак, Сыщик. Следующий шаг — сверить с его списком понравившегося, когда придёт.

Дубли истории: один фильм из двух файлов экспорта резолвился дважды (Кинопоиск и TMDb) —
теперь схлопываются и в `history()` (по внешним ID), и в генераторе при следующем прогоне.

Атрибуция: в настройках раздел «Откуда данные» (Wikidata, TMDb с обязательной фразой,
Кинопоиск, Open Library); в карточке под телом — подпись источника кадра.

## Разборы в карточке (22.09, по замечанию владельца)

Владелец спросил, схематичны ли одинаковые блоки в модальной карточке. Были схематичны:
до сих пор в них попадал только поиск по каналам авторов — четыре одинаковых прямоугольника
«разбор откроется, если он там есть». Теперь:

- **Конкретные разборы — материалом.** `ExternalAnalysis` получил `previewUrl`, а
  `ExternalAnalysisLink` — кадр ролика во всю ширину карточки (`.tm-extlink--preview`).
  Закрытый спойлерами разбор остаётся на месте, но кадр под размытием и штриховкой:
  видно, что материал есть, и не видно, о чём он.
- **Поиск по каналам — одной строкой** внизу (`SearchLine`, `DiscussionPlace.search`):
  это не разбор, а способ его поискать. Так же на экране «Произведение».
- **Порядок в карточке**: кадр → что это делает и почему вам → описание → разборы →
  места разговора → строка поиска → где посмотреть → действия.
- **В архиве разборы открыты**: просмотр закончен, спойлеров бояться нечего
  (`getJourney` кладёт их в запись, `JourneyEntryData.analyses`).
- **Данные**: `src/mocks/essays.ts` — 36 роликов к 28 фильмам из списка владельца,
  генератор `tools/build-essays.mts` (название и автор — из открытого oEmbed YouTube, кадр —
  штатная превьюшка ролика; к каналам не обращаемся). Ключ — `tmdb:<id>` фильма, а не ID
  карточки: одна и та же «Матрица» в истории, каталоге и пуле имеет разные ID.

- **Длительность, канал и дата** — из YouTube Data API (`YT_API_KEY` в `.env.local`, 50 роликов
  за запрос). В мете разбора теперь «elcinema · 64 минуты · рус. · со спойлерами»: разбор на час
  и разбор на восемь минут — разные решения.

**Индекс разборов по каналам** (`tools/build-essay-index.mts` → `src/mocks/essaysAuto.ts`).
Каналы берутся из уже известных роликов — ровно те, кого читает владелец (elcinema, ЭПИЗОДЫ,
КИНОЛИКБЕЗ, Nuke, «4то за Персонаж?», РЕЖУПРАВЛЕНИЕ); у каждого читается плейлист загрузок
(1 единица квоты на 50 роликов, всего около 1700 роликов), названия сопоставляются с нашими
произведениями. Это догадка, а не разметка, поэтому такие разборы помечены
`ExternalAnalysis.unverified` и показываются отдельной группой «Нашлось по названию — не
проверено». Подтверждать их должна кураторская.

Сопоставление русских названий в свободном тексте — приёмы из соседнего проекта `~/recruit`
(`apps/openclaw/openclaw/skills/role_hints.py`, `ner_extractor.py`), где так же ловят названия
должностей в постах:

1. левая граница закрыта (включая кириллицу), правая открыта — иначе «Прибытие» не ловится
   в «смысл ПРИБЫТИЯ», а склонения в заголовках роликов — норма;
2. слова-ловушки: у них это обычные английские слова среди названий инструментов, у нас —
   односложные названия («Зеркало», «Начало», «Игра»); им нужен более сильный вид: капсом,
   в кавычках или рядом с ярлыком («смысл», «разбор», «#КИНОЛИКБЕЗ»);
3. сторожа «рядом стоит конкурент» — снимают совпадение: «Тёмный рыцарь» рядом с «Джокером»,
   «Бэтмен:» перед «Началом», «удачи» после «Джентльменов»;
4. самое длинное совпадение побеждает: «Треугольник печали» важнее «Треугольника»;
5. ролики короче пяти минут отбрасываются — это шортсы, а не разборы.

6. название после ярлыка должно быть нашим: эти каналы пишут «смысл ПРИБЫТИЕ», «разбор фильма
   ИЗГОЙ», и если ярлык есть, а наше название стоит не при нём — разбирают другой фильм
   («ИГРА — это НАЧАЛО наоборот | смысл ИГРА» это про «Игру», а не про «Начало»).

Замер на том же прогоне: 59 совпадений без правил → 38 после границ и капса → 30 после
сторожей → 25 после починки сторожей → **33** после возврата регистронезависимости и правила
ярлыка. Две собственные ошибки по дороге, обе тихие: в JavaScript `\w` не знает кириллицы
(сторож «тёмный рыцарь» не срабатывал на «в Темном рыцаре»), а потерянный флаг `i` отрезал
все упоминания капсом — то есть основной стиль этих каналов («смысл ПРИБЫТИЕ»). Ложные
срабатывания, которые правила сняли: ролик про «Тёмного рыцаря» под «Джокером», «Бэтмен:
Начало» под «Началом», «Чёрное зеркало» под «Зеркалом», «Джентльмены удачи» под
«Джентльменами», «Пёс-призрак» под «Расёмоном», «франшиза на грани провала» под «На грани»,
«Прирождённые убийцы» под «Убийцей», «разбор фильма ИЗГОЙ» под «Посылкой».

Сами правила вынесены в `tools/title-match.mts` — ими пользуются два генератора.

**Посты Telegram — тем же способом** (`tools/build-telegram-index.mts` → `src/mocks/postsAuto.ts`):
`npx tsx tools/build-telegram-index.mts episodesfilm=~/Downloads/ChatExport_ЭПИЗОДЫ …`. Вход —
официальный экспорт из Telegram Desktop («Экспорт истории чата»), HTML или JSON: собственные
данные владельца, полученные штатной кнопкой клиента. С 23.09 к нему добавилась выемка по
MTProto (см. ниже), и генератор читает оба источника разом. Парсинг `t.me/s/<канал>` остаётся
запрещённым. Имя канала задаётся явно: в экспорте его нет, а
выводить из ссылок внутри постов нельзя — у elcinema рекламная ссылка встречается чаще
собственной. Прогон 22.09 по четырём каналам (@episodesfilm, @chtozapersonazh, @elcinemanew,
@nukedie): **4414 постов → 38 привязок к 21 произведению**.

Пост — не заголовок ролика, он гораздо шумнее, поэтому правил больше:

- название ищется только в первой строке (она у поста за заголовок): по всему телу ловятся
  упоминания, а не темы — «Паразиты» всплывают в посте совсем о другом;
- название должно быть выделено кавычками или капсом — сами каналы так и пишут; без этого
  «Помните, я обещал…» уходит в «Помнить», а «пять дней с легендой» — в «Легенду»;
- инфинитив не укорачивается основой («Помнить» → «Помнит» + хвост ловил «Помните»);
- анонс отсеивается от разбора: либо длинный текст, либо ярлык («смысл», «разбор», «почему»);
- не больше трёх разборов на произведение, самые содержательные, без повторов заголовка;
- в карточке пост и ролик с тем же названием схлопываются: канал анонсирует свой же ролик его
  заголовком, и это один разбор на двух площадках.

Точность всё равно ниже, чем у роликов: на глаз около семи из десяти против примерно девяти
десятых. Это ровно та причина, по которой автонайденное помечено и стоит в очереди на
подтверждение, а не подаётся как факт.

### Справочник фильмов: узкое место было не в правилах (22.09)

Первый прогон дал 21 произведение с разборами, и это выглядело как слабость правил. Замер
показал обратное: в четырёх каналах около 2400 постов выделяют название в первой строке,

### Проверка автонайденных разборов участниками (22.09)

Регексп привязывает ролик к фильму по названию и иногда врёт — значит, привязку должен
подтверждать человек. Это стало самым дешёвым заданием кабинета участника:

- вид задания `link_check` в контракте (`ContributorTaskKind`, payload `{ work, analysis }`,
  ответ `about_this | other_work | unsure`); компонент `LinkCheck` — кадр ролика, название,
  канал, длительность и три кнопки: «Да, про этот» / «Нет, про другой» / «Не могу сказать»;
- задания собираются из `essaysAuto` и `postsAuto` на лету (`src/mocks/linkTasks.ts`) и идут
  первыми в очереди: сейчас их 326, по двадцать секунд каждое. Сначала те произведения,
  которые участник видел сам или которые стоят у него в подборе — их разборы он увидит в
  карточках сегодня; справочник из мастер-списка уходит в хвост;
- вердикт применяется сразу: «про это» снимает пометку «не проверено» и поднимает разбор
  к подтверждённым, «про другое» убирает его из карточки. В моке вердикты живут до
  перезагрузки страницы, в продукте это запись на сервере.

Контур замкнулся: нашли автоматически → подтвердил человек → попало в карточку как
проверенное. Проверено в браузере end-to-end обеими ветками (22.09).

### Книги: ключ разбора и четыре канала о литературе (22.09)

Разборы привязывались только к фильмам: ключ был `tmdb:<id>`, а у книг TMDb ID нет — книжные
разборы падали в никуда. Теперь ключ зависит от вида произведения: у фильма `tmdb:<id>`,
у книги `isbn:<isbn>`. ISBN у книги не один (издания разные, разбор один), поэтому генератор
кладёт первый, а слой данных ищет по всем ISBN карточки. Общий список произведений для
генераторов вынесен в `tools/works-index.mts` (каталог, история, присланное просмотренное,
пул, справочник фильмов) — им пользуются оба индекса, а `worksByAnalysisKey` в `src/api`
собирает такую же таблицу для заданий «тот ли это фильм».

Каналы о литературе из списка владельца (22.09): **«Филолог всея Руси»** (@filologofrus,
YouTube @poetische), **«Логово Филолога»** (@logovofilologa), **«Я у мамы филолог»**
(YouTube @ya_u_mamy_filolog). Все заведены в `sources.ts` как `voice`; «Филолог всея Руси»
живёт на двух площадках и в карточке остаётся одним автором.

Что получилось: ролики — **185 привязок к 139 произведениям**, из них книжных ровно три
(«Имя розы» от КИНОЛИКБЕЗа, «Мастер и Маргарита» от ЭПИЗОДОВ и «Филолога всея Руси»);
из постов к книгам не привязалось ничего.

Первый прогон дал к книгам ещё пять постов — и все пять оказались про экранизации: «Каким
получился сериал по роману "Имя розы"», «#ФильмДня — "Имя розы"», «полная история
экранизаций "Мастера и Маргариты"». Разговор об экранизации — не разговор о книге, а фильма
у нас в базе нет, поэтому он прилипал к книге. Правило `ADAPTATION` в `title-match.mts`:
книжное совпадение снимается, если в заголовке «экранизац», «сериал», «фильм», «смотр»,
«режисс», «актёр». Фильмам это правило не нужно — обратной ошибки почти не бывает.
Узкое место то же, что было у фильмов до мастер-списка: **книг в базе семь**. Каналы говорят
о сотнях книг, привязывать не к чему. Нужен справочник книг — то же, чем `filmBase` стал для
фильмов: список «Автор — Название», прогнанный через Open Library (ключа не требует, ISBN
и обложки отдаёт). Список от владельца — и книжная половина начнёт работать сама.

### Сериалы: что нужно, чтобы их прорабатывать (22.09, интерфейс пока не делаем)

Сериалов в продукте нет и по решению владельца пока не будет. Состояние дел, чтобы не
искать заново:

- в контракте `WorkCard.type` — `'film' | 'book'`. Добавление `'series'` задевает `workMeta`,
  `searchLinks` (там стоит `work.type !== 'film'`), карточку и подбор — это уже интерфейс;
- импорт истории сериалы **узнаёт и откладывает**: `toJourneyEntries` кладёт их в `skipped`
  (у владельца это 12 сериалов с ID Кинопоиска из страницы «Оценки»). Данные не теряются
  внутри разбора, но никуда и не сохраняются;
- посты каналов о сериалах отсеиваются сами собой: привязывать не к чему, в базе их нет;
- дешёвый первый шаг, не трогающий интерфейс, — справочник сериалов рядом с `filmBase`
  (TMDb `/tv`, ID Кинопоиска резолвятся через Wikidata P2603) плюс сохранение отложенных
  сериалов из импорта. Тогда к моменту, когда тип появится в контракте, материал уже будет.

## Импорт с Кинопоиска: новая страница «Оценки и просмотры» (29.09)

Кинопоиск перевёл профиль на новую вёрстку (`/user/<id>/votes/?category=voted-watched`,
Next.js, по 20 карточек), старый `parseKinopoiskHtml` её не узнаёт. Новый разбор —
`parseKinopoiskProfile` в `lib/import/formats.ts`, узнаётся по `userVotedWatchedMovies`. Классы и
`data-tid` там хэшированные, поэтому разбор держится за структуру: ссылка `/film|series/ID/` с
постером → плашка оценки (нет плашки — «просто просмотрено») → ссылка-подпись «Название» +
«2014, жанр». Оригинала и даты на странице нет. `apolloState` в `__NEXT_DATA__` пустой — данные
только в разметке. Шторка импорта принимает такие файлы без изменений.

Для присланных владельцу страниц — `tools/import-kinopoisk.mts <ник в Telegram> <файлы|папки>`
→ `seeds/<ник>.json` (просмотренное + оценки 1–5 с `raw` 1–10), дальше `publish-seed.mts`.
Проверяет, что все файлы одного профиля Кинопоиска, и печатает пропуски и повторы страниц
(номер — из `__NEXT_DATA__.query.page`; ID профиля наружу не уходит). Сопоставление:
ID Кинопоиска → Wikidata P2603 (раз в секунду) → TMDb; иначе поиск TMDb по названию с годом ±1;
`--fast` — без Wikidata. Кэш `.cache/kinopoisk-resolve.json`. Сериалы — `l-tmdbtv<id>`, ключ
IMDb, как в `resolve-seed`. Записи помечены `from: 'kinopoisk'`: `resolve-seed` их и оценки
не затирает, а `import-kinopoisk` не трогает записи присланного списка. TMDb-клиент получил
`findTvByImdb`.

## Импорт истории (22.09, шторка сделана)

`ImportHistorySheet` — шторка из настроек («История» → «Импортировать историю»). Три входа
сразу: файлы выгрузок, просто список названий и то и другое вместе.

- **Разбор на клиенте.** Файл выгрузки профиля может содержать сессионные ключи — он не
  уходит никуда, ни в какой вид. Это сказано в самой шторке, а не только в документации.
- **Просто список названий** — новый формат `plain_list` (`parsePlainList` в `lib/import`):
  по названию в строке, год в конце необязателен, маркеры списка отбрасываются. Формат
  добавлен не от красоты: 70% просмотренного владельца пришло именно так.
  Распознаётся строго — иначе любой нераспознанный CSV молча стал бы «историей».
- **Отчёт «что поняли»** до импорта: сколько записей, фильмов, книг, с оценками; сериалы
  отложены отдельной строкой (типа в контракте нет), нераспознанные файлы — тоже.
- **Вопрос о норме шкалы**, когда в записях есть оценки: «какая оценка у вас значит
  „нормально"» с медианой по умолчанию. Уходит в `UserSettings.ratingNorm`, откуда его берёт
  `deriveScale`. Угадывать нельзя: у владельца медиана восьмёрка, а норма — семёрка.
- **Сверка со всем, что знаем**: каталог, история, присланный список и справочник из
  мастер-списка. Раньше сверка шла только по каталогу, и знакомый фильм уходил в резолвер по
  сети и заводился второй раз. На списке из шести названий теперь ноль сетевых запросов.
- Разбор идёт **на вводе**, а не по потере фокуса: иначе «Импортировать» остаётся неактивной
  ровно в тот момент, когда человек вставил список и тянется к кнопке.

Проверено в браузере: список из четырёх названий → четыре записи в архиве; выгрузка
Letterboxd на 88 оценок → отчёт и вопрос о норме.

## Вход через Telegram (22.09)

Мини-приложение отдаёт строку `initData`; подлинность доказывает `hash` — HMAC-SHA256 от
отсортированных пар на ключе `HMAC-SHA256("WebAppData", <токен бота>)`. Реализовано:

- `src/lib/telegramAuth.ts` — `parseInitData` (разбор, только чтобы показать имя) и
  `verifyInitData` (проверка подписи и свежести, сравнение без раннего выхода). Проверять
  обязан **сервер**: токен бота — это полный доступ к боту, в клиенте его нет и не будет;
  функция лежит здесь как эталон для бэкенда и для прогона.
- `src/api/index.ts` — `loginWithTelegram(initData)` разбирает строку, отсекает просроченную
  (сутки, как советует Telegram) и выдаёт `Session` с `verified: false`: подтверждать нечем.
  Плюс `loginAsDemo`, `getSession`, `logout`. В контракте — `AuthUser` и `Session`.
- `LoginScreen` внутри Telegram сам меняет `initData` на сессию и уходит на «Сегодня»;
  снаружи — ссылка на бота и демо-вход. В настройках появился раздел «Аккаунт»: кто вошёл,
  честная строка про неподтверждённую сессию и «Выйти».

Прогон подписи (`scratchpad/auth-test.mts`, 22.09): подлинная принимается, чужой токен,
подменённый `id`, отсутствующий `hash` и просроченная на сутки — отвергаются.

Про `my.telegram.org`: на аккаунт даётся **одно** приложение. Если оно уже создано, форма
нового молча отвечает ERROR — надо открыть `my.telegram.org/apps` и взять существующие
`api_id`/`api_hash`. Для входа они не нужны вовсе (там хватает токена бота на сервере) —
только для чтения каналов через MTProto.

## Ось регистра и присланный список просмотренного (22.09)

Участник прислал текстом 79 фильмов, которые смотрел (не «любимое»: оценок в списке нет,
по его словам большая часть около 7 из 10, часть 8–9, часть 5–6). Что из этого вышло:

- **Выгрузка покрывает 29% просмотренного.** Из 79 названий в кинопоисковой выгрузке нашлось
  23; остальные 56 модель не видела вовсе. Вывод для продукта: импорт истории не может быть
  только выгрузкой из сервиса — нужен приём простого списка названий (`ImportHistorySheet`,
  до сих пор не сделан). Резолвер списка — `tools/resolve-watched.mts` → `src/mocks/userWatched.ts`
  (TMDb-поиск, подсказка года, запасное написание через «е» вместо «ё»: «Чёрная смерть»
  в базе — «Черная смерть»). Сериалов в контракте нет, они из списка выброшены.
- **Что видно в списке, чего нет в выгрузке.** Регистр «Миф и обряд» — 41% против 19%,
  «Расследование» — 34% против 48%. То есть выгрузка с оценками систематически смещена:
  по ней участник выглядит любителем детективов, по полному списку — ещё и фольклорного ужаса.
- **Тональный регистр** (`Register` в контракте, восемь значений в `src/lib/registers.ts`) —
  ось вкуса, а не развития: «на каком языке произведение говорит». Вкус считается из выбора,
  а не из оценок (`deriveRegisterTaste`): доля регистра у участника против его доли в мире
  (`src/mocks/registerBase.ts` — 400 фильмов TMDb, популярное с 1960-го). Логарифм отношения,
  сжатый в ±1 и приглушённый при малом числе наблюдений. Сейчас: Телесное +0.7,
  Расследование +0.4, Миф и обряд +0.2, Без жанра −0.2, Приключение −0.6.
- **В подборе** регистр — третий вес: `SCORE_WEIGHTS` = уровень 0.4, операции 0.3, регистр 0.3.
  Плюс два ограничения, без которых вкус превращается в эхо: не больше двух кадров одного
  регистра в слейте и хотя бы один кадр на непривычном языке, если всё остальное — любимое.
  В объяснении регистр называется словами («И это старая жуть: обряд, лес, проклятие…»),
  а непривычный — честно: «Язык другой, чем обычно: …».
- **Разметка регистра в моках — заглушка**: `tools/build-registers.mts` выводит его из жанров
  и ключевых слов TMDb (`tools/register-tags.mts`) одинаково для истории, каталога, пула и
  присланного списка. В настоящем конвейере регистр ставит аннотатор; механический вывод
  взят потому, что иначе проверка подсматривала бы ответ.

**Шкала оценок у каждого своя** (замечание владельца 22.09: «у меня семёрка — норма, у другого
человека шкала может работать иначе»). Поэтому вес наблюдения считается не от абсолютного
числа, а от места оценки в собственном распределении участника — `deriveScale`:

- норма — то, что участник назвал сам (`UserSettings.ratingNorm`), иначе его медиана;
- ровно норма весит 0.55, выше — растёт до 1 по рангу среди его же высоких оценок, ниже —
  падает до 0.15 по рангу среди низких; «понравилось» = строго выше нормы;
- оценок меньше восьми — ровная линейка от нормы, без рангов.

У владельца это даёт 4:0.15 5:0.18 6:0.32 7:0.55 8:0.88 9:0.98 10:1.00. И сразу показывает,
почему норму нельзя угадывать: его медиана по выгрузке — восьмёрка, а нормой он называет
семёрку. Спрашивать её надо там же, где импортируются оценки (`ImportHistorySheet`).
Отдельная, более глубокая работа по шкале — в ROADMAP (этап 4, вместе с IRT).

**Чего эта ось не делает.** Оценки участника она не предсказывает: на 90 оценённых работах
выгрузки AUC «выше нормы против ниже нормы» (сама норма из проверки выброшена) — 0.54 у старой
формулы и 0.49–0.53 у любой версии с регистром, то есть монетка (`tools/watched-report.mts`).
Причина видна в тех же числах: средние по регистрам расходятся на четверть балла (7.13–7.69)
при 53 «восьмёрках и выше» против 19 «шестёрок и ниже».
Регистр объясняет, что участник вообще выбирает смотреть, а не как он это потом оценит.
Значит, качество подбора на выгрузке из сервиса померить нельзя — нужны данные, которые
собирает само приложение: шаг прогноза («сколько это потянет», сделан 23.09, см. ниже) и
причины брошенного. До этого любые веса в `SCORE_WEIGHTS` — решение дизайна, а не результат
замера.

## Шаг прогноза: чем мерить подбор (23.09)

Последний пункт первого этапа. Перед началом приложение задаёт один вопрос — «как думаете,
как пойдёт?» по той же трёхступенчатой шкале, что и вопрос после просмотра. Иначе сверять
нечего: шкалы должны совпадать.

- **Рядом с ответом участника кладётся ответ модели.** `expectedDifficulty(state, work, energy)`
  в `src/lib/model/recommend.ts` — разрыв между уровнем произведения и целью участника
  (комфорт плюс шаг по усилию), пороги те же, что у `levelFit`: разрыв в один уровень это
  ещё «в самый раз». Смысл в этом: сверять надо не участника, а нас. Участник отвечает про
  себя и ошибаться не может; ошибаемся мы.
- **Контракт**: `DifficultyPrediction { expected, model?, at }` и `JourneyEntryData.prediction`;
  `startWork(workId, expected?)`. В моке прогнозы живут в памяти сессии (ключ — id
  произведения), в продукте это запись на сервере в момент старта.
- **Где спрашиваем**: `PredictionStep` — один вопрос, «Начать» и «Пропустить и начать».
  В ленте он показывается в той же карточке вместо панели действий (шторка поверх шторки —
  плохо), на экране произведения и в маршруте — шторкой `PredictionSheet`. Пропуск в один
  тап: прогноз нужен нам, а не участнику, и задерживать его между «начать» и просмотром мы
  права не имеем.
- **Где сверяем**: `PredictionNote` в разборе чек-ина и в записи дневника. Участнику — одна
  строка без оценки («Вы ждали „легко“ — оказалось тяжелее»): это факт о произведении и о
  дне, а не ошибка человека. Строка про модель («Мы ждали „в самый раз“ — не угадали»)
  показывается только с включённой механикой: это наша внутренняя сверка.
- Прокликано по CDP обеими ветками (23.09): прогноз «тяжело» → факт «в самый раз» и прогноз
  «легко» → факт «тяжело», с механикой и без.

Чего это ещё не даёт: отчёта. Пока прогнозы живут до перезагрузки, считать по ним нечего —
первый настоящий замер («на скольких из N модель угадала») появится вместе с бэкендом,
который их сохранит. Зато формула, которую надо будет проверять, теперь записана в коде
и лежит рядом с той, что делает подбор.

## Граф соупоминаний: первая независимая проверка модели (23.09)

Разметка есть у 47 произведений из 1178, и похожесть по операциям сравнивать не с чем: всё,
что у нас было, мы сделали сами. Соупоминание — сигнал чужой: кого называют в одном посте,
решаем не мы, а те, кто пишет о кино. `tools/build-comention-index.mts` → `src/mocks/comentions.ts`.

**Названия ловятся наоборот, чем в индексе разборов.** Там важна тема поста и хватает первой
строки; здесь нужны все упоминания в теле, а перебирать 1178 названий по 60 тысячам постов
дорого и шумно. Поэтому из поста достаётся то, что выделено кавычками или капсом (каналы
названия выделяют всегда), и уже это ищется в таблице названий — строгим равенством после
нормализации. Точность тут важнее полноты: постов много, редкое упоминание не жалко.

Замер по четырнадцати каналам: **60 320 постов → 5500 с названием, 1041 с двумя и больше;
706 названных произведений, 280 пар с тремя и больше совместными упоминаниями.** Вес пары —
косинус `n / √(nₐ·n_b)`: без поправки «Паразиты» оказались бы соседом всего подряд.

**Что этот сигнал на самом деле ловит** — видно по верхушке: Тарковский («Сталкер» ↔
«Зеркало» ↔ «Солярис» ↔ «Иваново детство» ↔ «Андрей Рублёв»), Антониони («Затмение» ↔
«Приключение» ↔ «Красная пустыня»), Андерсон («Магнолия» ↔ «Ночи в стиле буги»), Макдона
(«Три билборда» ↔ «Залечь на дно в Брюгге») — и наградной сезон 2022 года («Власть пса» ↔
«Белфаст» ↔ «Король Ричард» ↔ «Вестсайдская история»). То есть соупоминание — это «один
автор, одна волна, один сезон», а не «одинаково устроено». В подписи к блоку так и сказано.

### Проверка: ось регистра держится на чужих данных

Регистр — единственная наша ось с приличным покрытием, и подбор на неё опирается (вес 0.3).
Вопрос: согласуется ли она с тем, как о кино говорят? Считаем долю пар, у которых есть общий
регистр, среди соупомянутых — и сравниваем со случайной парой **из тех же фильмов** (сравнивать
со всей базой нельзя: в графе оседают не случайные фильмы, а те, о которых пишут, и набор
регистров у них свой).

- пар, где регистр известен с обеих сторон, — **271**;
- общий регистр у **44%** из них против **26%** у случайной пары из той же выборки;
- разница **1.68×**, z = 6.6.

Это первый замер в проекте, который сделан не на наших же данных. Ось регистра он
поддерживает. Чего он не проверяет: уровень сложности и операции — их разметка по-прежнему
у 47 произведений, и пар с обеих сторон размеченных почти нет.

Чтобы проверка вообще стала возможной, регистр пришлось посчитать и для справочника:
`tools/build-registers.mts` теперь берёт и `filmBase` (TMDb-жанры и ключевые слова, кеш в
`.cache/tmdb-tags.json`, один запрос на фильм). Покрытие выросло с 207 произведений до
**1166** — до этого в графе было всего 8 пар с известным регистром, и никакой проверки
не получалось.

### В продукте

`CoMentionList` — блок «Рядом называют» на экране произведения, перед местами разговора:
это тоже про разговор, но про то, что в нём звучит, а не про то, где он идёт. Пять названий
со ссылками, подпись честно говорит, что это не похожесть и не совет. В мок идут соседи
только тех произведений, которые участник видит (157), иначе в бандл уехал бы весь граф;
`standalone.html` вырос с 2004 до 2089 КБ.

Попутно починено: `getWork` не знал присланного просмотренного, и ссылка на «Сталкера» из
соседей упиралась в «такого произведения нет».

## TV Tropes: замер вместо ожиданий (23.09)

Вопрос был один: закроет ли TV Tropes главную дыру — разметку (43 произведения из 1046)?
Замер сделан на датасете `dhruvilgala/tvtropes` (статья «Analyzing Gender Bias within Narrative
Tropes», 2020; 650 МБ, таблицы троп ↔ фильм с IMDb ID). Наша база сведена с ним по IMDb;
недостающие IMDb ID добраны из TMDb (`tools/backfill-imdb.mts` → `.cache/imdb-by-tmdb.json`,
1030 из 1039). Замер воспроизводится: `tools/tropes-report.mts`.

**Числа (23.09):**

- в таблице 390 511 строк, 8796 фильмов; **наших найдено 420 из 1030 (41%)**;
- тропов на фильм: медиана 55, от 1 до 1292, всего 52 075 привязок;
- из 43 размеченных вручную покрыто **12** — золотого набора для проверки почти нет;
- разных тропов 15 154, из них 5903 встречены один раз;
- **топ-200 тропов покрывают 12% привязок**, топ-1000 — 32%, топ-3000 — 56%.

**Вывод: разметку этим не закрыть.** Три причины, каждая видна в числах.

1. Хвост. План «разметить топ-200 тропов и получить операции» упирается в то, что топ-200 —
   это 12% сигнала. Чтобы покрыть половину, нужно три тысячи ручных сопоставлений.
2. Голова хвоста — не про восприятие: `shoutout`, `creatorcameo`, `hollywoodhypemachine`,
   `titledrop`, `largeham`. Это производственные мелочи и тон, а не когнитивные требования.
   Полезные там есть (`foreshadowing`, `chekhovsgun`, `whamline`, `bookends`), но они тонут.
3. Глубина разметки — это популярность, а не сложность: у «Начала» 686 тропов, у «Паразитов» —
   10, у «Соляриса» — 14. Считать по числу тропов что-либо про устройство фильма нельзя:
   померишь размер фанбазы.

**Что TV Tropes даёт на самом деле — и это ценно.** Проверили, согласуется ли он с графом
соупоминаний: берём пары нашего графа (кого называют вместе русские каналы) и считаем, насколько
у них общие тропы (Жаккар) по английской вики.

- пар, где тропы известны с обеих сторон, — 31;
- сходство по тропам: **0.060 против 0.006** у случайной пары из тех же фильмов;
- перестановочный тест на 20 000 выборках: **p < 0.0001**.

Два совершенно независимых источника — русские телеграм-каналы и англоязычная фан-вики —
говорят об одном и том же. Это второй за два дня замер, сделанный не на наших данных
(первый — ось регистра). Пар всего 31, поэтому это указание, а не закон, но эффект
десятикратный и устойчивый к перестановке.

Отсюда роль источника: **тропы — это материал для карточки** (там длинный хвост не мешает:
нужно два-три приёма на произведение, а не полная таксономия) **и третий независимый сигнал
похожести**, а не способ получить операции и уровень. Как это сделано — ниже, в разделе
«Приёмы в карточке».

**Лицензия.** Контент TV Tropes — CC BY-NC-SA (с июля 2012; до этого CC-BY-SA). NonCommercial
встаёт в тот же ряд, что TMDb, IMDb datasets, Trakt и MovieLens в разделе «Риски» ROADMAP.
ShareAlike опаснее: производная разметка от их текста тянет за собой то же условие. Поэтому
у себя держим ID, названия, структурные связи и собственные производные признаки — не тексты.

## Пересказы сюжетов: CMU замерен, а брать надо Википедию (23.09)

Задача была взять CMU Movie Summary Corpus как вход для будущей автоматической разметки.
Корпус взят и замерен, и замер развернул решение.

**CMU: 545 наших фильмов из 1039 (52%).** Разложение по времени объясняет всё:
**до 2013 года — 537 из 700 (77%), 2013-й и новее — 8 из 339 (2%)**. В README корпуса написано
прямо: пересказы извлечены из дампа английской Википедии **от 2 ноября 2012 года**. То есть
это не отдельный источник, а замороженный снимок Википедии тринадцатилетней давности. Треть
нашей базы новее и не появится там никогда. Сводить его приходится по названию и году: ни IMDb,
ни TMDb в нём нет, а Freebase, на который он ссылается, мёртв.

**Признаки пересказа сами по себе не несут почти ничего** (`tools/cmu-report.mts`):

- длина пересказа против нашего замера формы по субтитрам (490 фильмов): ρ = −0.04 и −0.01 —
  ноль. Пересказ — про то, **что** происходит; наша дыра — про то, **сколько** произведение
  требует, и эти две вещи не пересекаются;
- против «нагрузки» по тегам Tag Genome (535 фильмов): длина ρ = 0.07 (p = 0.13), имён в
  пересказе ρ = −0.05. Тоже ноль;
- **единственное живое** — число ролей из `character.metadata.tsv`: ρ = 0.15, p = 0.0006.
  Слабо, но по-настоящему, и этого не дают ни субтитры, ни тропы: сколько людей надо держать
  в голове;
- против ручной разметки (12 фильмов): длина ρ = −0.63 при p = 0.033 — знак **отрицательный**
  (у сюжетных блокбастеров пересказ длиннее, у «Соляриса» короче), но при четырёх проверках
  и n = 12 это ничего не доказывает.

**Зато сам текст оказался лучше, чем я ожидал.** Пересказ «Помни» начинается словами:
«A backwards sequence is shown… black-and-white and color sequences, with the black-and-white
sequences taking place chronologically before the color sequences». То есть когда фильм
рассказан необычно, Википедия это описывает — редакторы пишут про устройство, а не только про
фабулу. Значит, как вход для разметки операций текст годится; бесполезны именно **числовые
признаки** пересказа, а не он сам.

**Методологическая ловушка, которую надо назвать вслух.** Из наших размеченных руками
произведений в корпусе есть 12, и это «Помни», «Малхолланд Драйв», «Расёмон», «Начало»,
«Детонатор» — фильмы, которые любая языковая модель знает и без пересказа. Проверить на них,
достаточно ли пересказа, невозможно: модель ответит по памяти. А там, где пересказ реально
нужен — на малоизвестном, — у нас нет эталона, с которым сравнивать. Это не довод против
разметки, это требование к её проверке: эталон придётся делать на фильмах, которые модель
знает плохо.

**Решение: источник — Википедия, а не CMU.** Раз пересказы всё равно оттуда, надо идти
к источнику. `tools/build-plot-summaries.mts`: наш IMDb ID → Wikidata (`P345`) → статья
в ru/en Википедии → раздел «Сюжет». Ключ точный, текст текущий, язык русский — тот самый,
на котором разметка и будет читаться. Проверка на выборке из 80 фильмов: статья есть
у 37 из 40 свежих (после 2012) и у 40 из 40 старых.

## Приёмы в карточке: белый список вместо отбора по частоте (23.09)

Тропы в карточку. Первым делом проверил, можно ли отбирать их автоматически — оказалось,
что нельзя, и это отдельный результат.

**Отбор по частоте не работает, по редкости тоже.** Частые приёмы — общие места
(`Foreshadowing` у 634 фильмов). Редкие — случайная мелочь: у «Бойцовского клуба» 451 приём,
и самые редкие из них — `Marshmallow Hell`, `Scary Teeth`, `Fist Of Rage`. Тогда попробовал
взвесить длиной разбора на вики (её мы считаем сами, текст не сохраняем): стало лучше, но
в голове списка всё равно встало производственное и прокатное — посмотрел, что вообще попадало
бы в карточки наших фильмов при таком отборе, и увидел `Career Resurrection`·18,
`Oscar Bait`·10, `Director's Cut`·9, `Tom Hanks Syndrome`·8, `Recut`·7, `Billing Displacement`,
`Chronically Killed Actor`. Дело не в сортировке: **страницы TV Tropes в основном про
производство и приём публикой**, приёмы повествования там в меньшинстве.

**Поэтому белый список, а не стоп-лист.** `tools/trope-dictionary.ts` — 78 приёмов, отобранных
руками: финал и развязка, ненадёжность рассказчика, устройство времени, расставленные заранее
детали, как снято, из чего сделан мир и разговор. Мы решаем, что считается приёмом, о котором
стоит сказать зрителю; TV Tropes отвечает, есть ли он в фильме. Внутри списка порядок задаёт
длина разбора: где написан абзац — приём разобран всерьёз, где строчка — проставлен мимоходом.

**Результат: 289 фильмов из 1030** (69% от тех 420, что вообще есть в датасете), медиана
3 приёма, два и больше — у 213. Из словаря пригодилось 75 приёмов из 78. Примеры:

- «Начало» — Предвестие, Ломает голову, Зритель узнаёт последним, Ружьё на стене, Открытый финал;
- «Солярис» — Сюжет-головоломка, Камера не выключается, Место как персонаж;
- «Сияние» — Предвестие, Глазами помрачения, Чудо или совпадение, Открытый финал, Фраза-удар;
- «Бойцовский клуб» — Предвестие, Герои знают, что они в фильме, Четвёртой стены нет,
  Ненадёжный рассказчик, Обращение к зрителю;
- «Догвилль» — Минимализм.

**Это не `TropeInsightData`, и путать нельзя.** В `tropeInsights` лежит утверждение о том,
**как** приём работает в произведении (`usage`, операции, объяснение) — это наша разметка.
Датасет такого не даёт вовсе. Поэтому заведён отдельный тип `TropeMention` и отдельный блок
в карточке, с оговоркой прямо под заголовком: «там сказано, что приём есть, но не как он
работает именно здесь, — и человеком это не проверено». Приём, уже разобранный руками,
из списка убирается, чтобы не стоял в карточке дважды.

**Спойлеры размечены в словаре руками** и проходят через тот же `SpoilerGuard`, что и
разборы: «Открытый финал», «Зритель узнаёт последним», «Всё оказалось сном» — уровень 2,
«Предвестие» и «Ружьё на стене» — 1, «Длинный план» и «Минимализм» — 0. Проверено в браузере:
у непросмотренного «Соляриса» «Место как персонаж» прячется под шторку, у просмотренного
«Начала» открыто всё.

**Лицензия.** Из датасета наружу идут только идентификатор, английское имя приёма и ссылка
на его страницу. Русские названия и объяснения — свои: тексты TV Tropes под CC BY-NC-SA,
и ShareAlike потянул бы то же условие на нашу собственную разметку. Подпись с указанием
авторства стоит под блоком.

**Следующий шаг, если понадобится:** `trope_check` в кураторской — контракт для него уже есть
(`ContributorTaskPayload`, `AnnotationProvider: 'tvtropes'`), а словарь и есть готовый вход:
человек подтверждает приём и проставляет `usage`, и подтверждённое переезжает из
`tropeMentions` в `tropeInsights`.

## Субтитры: форма фильма, посчитанная, а не описанная (23.09)

После TV Tropes стало видно, чего не хватает: чужие теги говорят, **о чём** фильм, а дыра у нас
в том, **сколько он требует** — `complexityLevel` проставлен у 43 произведений из 1046. Признаки,
которые считаются механически, метят ровно туда. ROADMAP §3 это предусматривал
(«вычислимые признаки … кинометрика для фильмов»), руки дошли сейчас.

**Источник.** Корпус OPUS OpenSubtitles v2024, русская дорожка (Lison & Tiedemann, свободен для
исследований). Архив — 3.8 ГБ, но качать его целиком незачем: object storage честно отдаёт
Range, поэтому берём оглавление zip (29.5 МБ) и потом только нужные файлы. Весь замер обошёлся
примерно в 120 МБ трафика и четыре минуты. Тексты субтитров у себя не храним — только числа.
Чтение корпуса: `tools/opus-subtitles.mts`; замеры: `tools/build-subtitle-metrics.mts` →
`.cache/subtitle-metrics.json`.

**Покрытие: 898 наших фильмов из 1030 (87%), с пригодными субтитрами — 889 (86%).**
Для сравнения: TV Tropes — 41%. Многодисковых обрезков среди наших не оказалось ни одного.
На фильм приходится до трёх переводов, метрика берётся как медиана по ним.

**Что считаем:** слов в минуту, доля времени под репликами, средняя длина реплики, слов в
реплике, доля хронометража в перерывах длиннее 30 секунд, самый долгий перерыв, средняя длина
слова, разнообразие словаря (TTR) и доля слов вне пяти тысяч самых частых в самом корпусе
(внешний частотный словарь не нужен: «редкое» нам интересно относительно того, как вообще
говорят в кино).

**Метрика не выдумана — она узнаёт фильмы.** Самые говорливые: «Омерзительная восьмёрка» (114
слов/мин), «Свидетель обвинения», «Большой Лебовски», «Социальная сеть», «Игра на понижение»,
разговорные документалки. Самые молчаливые: «Новые времена» (6), «Побудь в моей шкуре»,
«Предел контроля», «Только бог простит», «Фотоувеличение», немое кино. У «Соляриса» 14 слов в
минуту, две трети хронометража без реплик и самый долгий перерыв 8.4 минуты; у «Двенадцати
разгневанных мужчин» при тех же 39 словах в минуту тишины всего 13%.

**Сколько в числе шума.** Один фильм лежит в корпусе в нескольких переводах — расхождение между
ними и есть ошибка измерения. Медиана расхождения по плотности речи — 2.7 слова в минуту,
90-й процентиль — 16.3, а разброс между фильмами — 15.2 (ст. отклонение). То есть шум примерно
вшестеро меньше сигнала. У отдельных фильмов расхождение большое («Прибытие» — 23), поэтому
в карточке оно показывается: число не должно выглядеть точнее, чем оно есть.

**Проверка против разметки руками — не прошла, и это надо сказать прямо.** Размеченных фильмов,
попавших в замер, всего 35. Из восьми осей только доля долгих пауз дотягивает до p = 0.041
(ρ = 0.35), а порог с поправкой на восемь проверок — 0.0063. **Связь с уровнем сложности не
подтверждена.** Направление при этом согласованное: по уровням 4 → 9 плотность речи падает
39 → 39 → 36 → 34 → 30 → 27, доля долгих пауз растёт 25% → 31% → 33% → 34% → 44%. Похоже на
правду, но на 35 фильмах доказать нельзя. Чтобы закрыть вопрос, нужно порядка 150 размеченных
фильмов — и метрика же подсказывает, каких: брать не подряд, а по всему диапазону.

**Проверка против графа соупоминаний — прошла уверенно.** 248 пар (у тропов было 31). Среднее
расстояние по форме между фильмами, которые русские каналы называют в одном посте, — 2.522;
у случайной пары из тех же 147 фильмов — 2.982; перестановочный тест на 20 000 выборках даёт
p < 5·10⁻⁵. **Третий за два дня замер не на наших данных** (первый — ось регистра, второй —
тропы): то, как о кино говорят, и то, как кино устроено по форме, сходятся.

**Участник отличается от справочника.** У просмотренного им реплики короче (−0.28 σ) и в них
меньше слов (−0.37 σ), долгих пауз чуть больше (+0.17 σ). Это первый признак вкуса, который
считается по форме, а не по жанрам, — и он готов к тому, чтобы войти в подбор.

**По регистрам разброс слабый**, но осмысленный: `absurd_satire` — 43 слова в минуту,
`folk_gothic` — 32 при 35% долгих пауз. Ось регистра и ось формы меряют разное, как и задумано.

**Что попало в продукт.** Тип `FilmForm` (§16), `src/mocks/filmForm.ts` (889 фильмов,
генератор `tools/build-film-form.mts`), компонент `FilmFormNote` и блок в карточке
произведения — перед разборами: замер помогает решить «сегодня или не сегодня» раньше, чем
чужое мнение. В карточке только числа, место среди 889 измеренных и оговорка, что это замер
формы, а не оценка сложности. Выводить «сложно» из плотности речи мы права пока не имеем.
Замер воспроизводится: `tools/subtitles-report.mts`.

**Кинометрика (длина плана) — в дальний бэклог** (решение владельца, 23.09). Публичной
выгрузки у Cinemetrics не существует: сайт переехал в Чикаго на движок OCHRE и данные отдаёт
только XQuery-эндпоинт их фронтенда (`ochre.lib.uchicago.edu/ochre/v2/ochre.php`). База набрана
добровольцами вручную, смещена к классике и немому кино, одна отправка на фильм — покрытие
наших 1030 скорее всего низкое. Считать длину плана самим (TransNetV2, PyCinemetrics) нельзя:
нужны сами фильмы. Если вернёмся — начинать с письма в Cinemetrics про выгрузку, а не с запросов
к их базе.

## Посты обновляются сами: MTProto вместо ручного экспорта (23.09)

До сих пор посты приходили официальным экспортом Telegram Desktop: владелец вручную выгружал
историю четырнадцати каналов, генераторы её читали. Для первой сборки это правильно, но
обновляться так нельзя — никто не будет выгружать пятнадцать каналов каждую неделю.
Теперь тот же материал берётся штатным клиентским API от лица владельца: его аккаунт,
его подписки, публичные каналы, которые он и так читает.

**Ключи и сессия — из соседнего проекта `~/recruit`** (решение владельца). `TG_API_ID`,
`TG_API_HASH`, `TG_SESSION_PATH` берутся из окружения, а если их там нет — из
`~/recruit/apps/openclaw/.env.openclaw` (путь задаётся `--env`). Значения только читаются:
в лог идут имена каналов и числа, ключи не печатаются и никуда не передаются. Путь к сессии
в env относительный, поэтому считается от папки самого env-файла. Файл сессии копируется во
временную папку и открывается копия — у соседнего проекта свой бот может держать оригинал
открытым, и SQLite этого не любит (их же урок из `check_dead_channels.py`).

**Чего скрипт не делает:** не парсит `t.me/s/<канал>`, не вступает в каналы, не читает
переписку, не трогает ничего, кроме перечисленных каналов, и не пишет в Telegram вообще
ничего.

**Бережность.** Резолв канала по имени — самая дорогая операция, за неё прилетает FloodWait
(в recruit это однажды стоило 16,5 часов простоя). Поэтому id каналов кешируются в
`.cache/telegram/peers.json` и второй прогон не резолвит ничего. Между каналами пауза,
за прогон не больше `--limit` постов на канал, `FloodWaitError` не глушится: прогон
останавливается, состояние уже сохранено, следующий раз продолжит с той же точки.

**Как читается.** `.cache/telegram/state.json` держит последний прочитанный id по каналу.
Первый прогон берёт хвост (`--backfill`, по умолчанию 400) — остальное уже лежит в экспорте;
дальше идёт только то, что новее. Выход — `.cache/telegram/<канал>.json` сразу в том виде,
какой читают генераторы: отдельный формат, а не подделка под экспорт Desktop, потому что в
JSON-экспорте теряются заголовок и сайт превью, а по ним генераторы узнают ролик и статью.

**`readExport` теперь принимает несколько путей через запятую** и сливает посты по id —
канал читается сразу из старого экспорта и из свежей выемки, пересечение не удваивается.
Список каналов переехал из истории шелла в `tools/telegram-channels.json`: генераторы
без аргументов читают его. Держать такой список в шелле — верный способ однажды пересобрать
индекс не по тем каналам.

**Папки `~/Downloads/ChatExport_*` удалять нельзя** (замер 24.09). Корпус — это экспорт
Telegram Desktop **плюс** кэш шлюза, они сливаются по id, и архив живёт только в экспортах:
шлюз держит свежую историю (8561 пост на 32 канала, ~270 на канал), а экспорт Кинопоиска

### Первый повторный прогон сломался — и почему (23.09, вечер)

Второй запуск выдал «канала нет» по четырнадцати каналам из двадцати. Причина не в Telegram
и не в правах: кеш хранил **один `id` канала**, а по голому числу Telethon канал не находит —
нужен ещё `access_hash`, и живёт он в кеше сессии. Сессию мы каждый раз копируем из соседнего
проекта во временную папку и после прогона выбрасываем, вместе с ней выбрасывался и `access_hash`.
Шесть каналов, которые всё же прочитались, были известны исходной сессии recruit — отсюда
и обманчивая частичность отказа.

Починка: в `peers.json` теперь лежит пара `{id, access_hash}` плюс название. Старые записи
(одно число) отбрасываются при чтении. Резолв по имени делается один раз на канал, дальше
не делается вовсе — защита от FloodWait осталась. Проверено: прогон по всем двадцати каналам
проходит без единого резолва.

Заодно нашёлся второй список каналов: в `telegram-fetch.py` был свой `DEFAULT_CHANNELS`, и он
уже разошёлся с `tools/telegram-channels.json` — пять каналов, добавленных вечером, попали
в JSON и не попали в Python, `--discussions` их молча пропустил. Теперь список один:
скрипт читает тот же JSON, что и генераторы.

## Tag Genome: похожесть по чужим описаниям (23.09)

После субтитров остался вопрос, который тропы не закрыли: есть ли источник, где разметка
**плотная** — не «встречается ли приём», а «насколько это про него», и по всем произведениям
сразу. Tag Genome 2021 (GroupLens) устроен именно так: 1084 тега, у каждого фильма значение по
каждому тегу, 10.5 млн оценок. Для сравнения у TV Tropes 15 154 тега, половина встречена
один раз.

**Как взяли.** Архив 1.8 ГБ, нужны три файла из него — снова Range-запросы через
`tools/remote-zip.mts` (тот же приём, что с субтитрами; ради него чтение zip по HTTP вынесено
в отдельный модуль). Скачано 95 МБ вместо 1.8 ГБ, из них 320 МБ распакованной таблицы
прочитаны потоком. Сырьё лежит в `.cache/taggenome/`, в репозиторий не попадает.

**Покрытие: 674 наших фильма из 1030 (65%).** В MovieLens вообще есть 899 (87%), но значения
Tag Genome посчитаны не для всех — только для 9734 фильмов. Ряд по покрытию теперь такой:
субтитры 86% → Tag Genome 65% → TV Tropes 41%.

**Главный результат — не про теги, а про субтитры.** «Медленно» (заранее заявленный набор:
`slow`, `atmospheric`, `meditative`, `dreamlike`) сошлось с нашим вчерашним замером речи на
605 фильмах: со словами в минуту ρ = −0.22, с долей долгих пауз ρ = +0.34, оба p < 5·10⁻⁵.
Англоязычные зрители MovieLens руками размечали то же, что мы автоматически посчитали по
русским субтитрам. **Замер формы подтверждён извне, на 605 фильмах, а не на 35.**

**Против графа соупоминаний — тоже прошло.** 44 пары: сходство по тегам у названных вместе
0.336 против 0.027 у случайной пары из тех же 48 фильмов, p < 5·10⁻⁵. Двенадцатикратный эффект.

**Друг друга источники не дублируют.** На 4000 случайных пар связь между «похожи по тегам» и
«близки по форме» — ρ = −0.03. То есть теги и субтитры меряют разное, и держать оба осмысленно.

**«Нагрузка» против разметки руками — снова не подтвердилась.** Заранее заявленный набор из
13 тегов (`thought-provoking`, `cerebral`, `confusing`, `complicated`, `complex`,
`philosophical`, `intellectual`, `nonlinear`, `non-linear`, `multiple storylines`, `allegory`,
`mindfuck`, `surreal`) дал ρ = 0.25 при p = 0.31 — но размеченных фильмов, попавших в набор,
всего **19**. Это третий раз, когда упираемся в одно и то же: **проверять сложность не на чем.**
При этом все уровни лежат выше среднего по «нагрузке» (от +0.02 до +1.56 σ) — то есть набор
тегов отличает «то, что мы вообще взялись размечать» от остального, просто не упорядочивает
внутри. Вывод прежний: нужно ~150 размеченных фильмов, отобранных по диапазону, а не подряд.

**Что теги говорят про участника.** Просмотренное им сильнее обычного по `twist`,
`twist ending`, `supernatural`, `stage magic`, `gory` — и слабее по `criterion`, `golden palm`,
`oscar`, `character study`, `talky`, `melancholy`, `1970s`. Это третье независимое
подтверждение одного и того же факта о вкусе (первое — ось регистра, второе — короткие реплики
по субтитрам). Рядом в том же списке стоят `idiotic`, `no plot`, `pointless`, `bad script`,
`predictable`: это **мнение аудитории MovieLens о жанровом кино**, а не свойство фильмов, и оно
ровно объясняет, почему рейтинговый консенсус этому участнику бесполезен. Отбор тегов здесь
сделан по величине разницы, поэтому это описание, а не проверка.

**Регистры в пространстве тегов различимы слабо**: пары с общим регистром 0.043 против −0.016
у разных. Оси разные, как и задумано.

**Что попало в продукт.** `src/mocks/tagNeighbours.ts` (674 фильма, до пяти соседей с близостью
не ниже 0.25), тип `TagNeighbour`, компонент `TagNeighbourList` и блок «Описывают похоже»
в карточке — сразу за «рядом называют». Два списка соседей из разных миров стоят рядом
намеренно: у «Соляриса» по тегам — «Сталкер», «Зеркало», «В прошлом году в Мариенбаде»,
«Женщина в песках», «Внутренняя империя»; у «Помни» — «Донни Дарко», «Подозрительные лица»,
«Бойцовский клуб», «Начало», «Олдбой». Расхождение между списками само по себе информация.
Замер воспроизводится: `tools/taggenome-report.mts`.

под блоком) плюс запрет коммерческого использования. ShareAlike нет, производная разметка

## Лента по кадрам и поиск с отметкой «смотрел» (23.09)

Две правки во фронтенде, обе — по просьбе владельца продукта.

**Лента листается блоками.** `.tm-stream` в приложении получила `scroll-snap-type: y mandatory`,
каждый баннер — `scroll-snap-align: start` и `scroll-snap-stop: always`: палец отпускается —
лента доводит фильм до верха экрана и дальше одного фильма за жест не проскакивает. Тонкость,
из-за которой это не работало с первого раза: строка «Архив · N записей» тоже должна быть точкой
привязки (`.tm-stream__archive { scroll-snap-align: start }`). Лента при отрисовке прокручена
программно на высоту этой строки (`main.scrollTop = ARCHIVE_ROW`, `TodayScreen`), а при
`mandatory` браузер тут же тянет прокрутку к ближайшей точке — если строка точкой не была,
прокрутка возвращалась к нулю и архив снова висел на экране. При `prefers-reduced-motion: reduce`
привязка выключена: доводка — это движение, которого человек мог попросить не делать.
Проверено по CDP: `snapType "y mandatory"`, `scrollTop 56`, точки привязки `[56, 184, 416, 648]`.

**Поиск фильмов и отметка «смотрел».** Новый экран `/search` (`SearchScreen`, пункт меню между
«Сегодня» и профилем): строка ввода липнет к верху, запрос уходит в `searchWorks` через 250 мс
после последнего нажатия, у каждой строки — кадр, название, год и кнопка «Смотрел / Убрать».
Пустой запрос показывает не пустоту, а сам список просмотренного с его размером — экран сразу
отвечает на вопрос «что у меня уже отмечено». Нажатие применяется сразу, не дожидаясь ответа
`api`, и поднимает тост с «Вернуть»; отказ сервера откатывает строку обратно.

В `api` добавлены `searchWorks(query, limit)` → `SearchHit[]` и `setWatched(workId, watched)`.
Ищется по всему, что знает мокнутый слой (каталог, история, пул подбора, просмотренное,
`filmBase`), ключ сравнения нормализован: диакритика снимается через NFD, «ё» приравнивается
к «е». Правка просмотренного живёт в памяти вкладки — `watchedAdded` и `watchedRemoved` поверх
мока, всё чтение просмотренного идёт через `watchedNow()`, новые отметки становятся в начало
списка. Бэкенда нет, перезагрузка страницы отметки теряет, и это честное состояние дела, а не
недоделка: когда появится сервер, менять придётся только эти две функции.

Проверено по CDP, в том числе сквозным сценарием без перезагрузки (переходы по `location.hash`,
иначе состояние `api` в памяти сбрасывается): лента до отметки — «Солярис», «Воспоминания
об убийстве», «Сыщик»; отмечаем «Воспоминания об убийстве» просмотренным на `/search`;
лента после — «Солярис», «Сыщик», «Анатомия падения», фильм из подбора ушёл. `npx tsc --noEmit`
чисто, `npm run build` проходит.

## Разборы по авторам: строка иконок вместо стопки превью (23.09)

Замечание владельца: под баннером идёт преамбула и сразу ролики, два превью занимают весь
экран, а сначала надо показать, **кто вообще разбирал этот фильм**. Решение — строка иконок
каналов, под ней один материал выбранного, ниже — Telegram.

**Считали до того, как рисовать.** Материал есть у 351 фильма, но у 135 из них — только
площадки (Кинопоиск, Okko, Wink, KION, viju): это анонсы своих премьер. Авторский канал есть
у 216 фильмов, и у 165 из них он ровно один; два и больше — у 51, три и больше — у 16.
Каналов 41, постов 449 (353 своих текста, 45 — ссылка на свой же ролик, 51 статья). Отсюда
главный вывод: строка нужна не ради «много каналов», а ради того, чтобы карточка показывала
**одну вещь за раз**, и обязана красиво вырождаться в один канал — иначе она сломана в трёх
случаях из четырёх.

**Единица — автор, а не платформа.** Владелец спросил, как сделать, чтобы при выборе
ютуб-канала показывался и его телеграм, и наоборот. Обратная механика не нужна, если завести
автора с выходами: один человек ведёт канал на YouTube, канал в Telegram и чат при нём.
Выбрали ролик — в строке выходов чип Telegram; смотрите пост — там чип YouTube. Проверено на
«Гаттаке»: пост ЭПИЗОДОВ, выходы «YouTube / Telegram».

Справочник — `tools/voice-dictionary.ts` (руками) → `tools/build-voices.mts` →
`src/mocks/voices.ts` (30 авторов: 23 автора, 5 площадок, 2 студии). Руками — потому что
автоматически это не выводится: на YouTube канал зовётся «4то за Персонаж?», в Telegram —
«Что за персонаж?», а в поле `author` у поста может стоять тот, у кого пост **переслан**
(«Искусство кино» внутри Cinemaholics, «Paramount Pictures» внутри ЭПИЗОДОВ). Поэтому ключ
привязки — канал, где материал лежит: `tg:<handle>` из id поста (`tg-episodesfilm-95`) и
`yt:<название канала>` у роликов. Чужое имя не теряется — оно идёт строкой «кто автор», но
имя того же канала на другой площадке за чужое не считается (`creditOf` в

## Фронтенд-пакет: семь правок после оценки приложения (23.09)

Владелец: «фронтенд целиком, потом всё остальное». Семь пунктов из §7 `ROADMAP.md`, все
сделаны и проверены по CDP.

**1. Преамбула в три строки.** `LeadText` (`src/components/LeadText.tsx`) обрезает объяснение,

только если текст правда не поместился: меряем высоту (`scrollHeight > clientHeight`), а не
длину строки — ширина строки на телефоне и на планшете разная. Замер: 72 px из 263 px,
после «Ещё» — 263 px и «Свернуть».

**2. Страница автора `/voice/:id`.** `VoiceScreen` + `getVoiceWorks` в api: всё, что автор
разбирал из того, что мы знаем, свежее сверху, непроверенные привязки помечены. Вход — чип
«Все разборы» в карточке; он есть только у авторов из справочника, потому что у самодельного
(канал, которого мы не знаем) страницы нет. Проверено: чип ведёт на `#/voice/chtozapersonazh`
(«Что за персонаж?», 21 фильм), у ЭПИЗОДОВ — 67 фильмов.

**3. Чек-ин в один тап из ленты.** Под баннером того, что смотрите сейчас, — строка «Как
пошло?» с «Закончил» и «Бросаю». Раньше до чек-ина было два шага через карточку, и он просто
не случался; без него петля «прогноз → как оказалось» остаётся пустой, а она и есть
единственный способ узнать, работает ли подбор.

**4. Пустая карточка объясняет, почему пуста.** После решения 23.09 площадки в разборы не
идут, и у 135 фильмов не осталось ничего. Вместо пустоты — строка «Из авторов об этом фильме
пока никто не говорил» и оговорка, что анонсы площадок сюда не идут. Проверено на «Сыщике».

**5. Форма фильма — линейкой, а не только числом.** Две шкалы с меткой (речь и тишина) и
подписанными краями: это замер, а не оценка, поэтому у шкалы подписаны оба конца, а не
«хорошо/плохо». Числа остались строкой ниже. На «Приглашении»: речь 73%, тишина 42%.
Настоящая «плёнка фильма» (темп по минутам) потребует перевыемки субтитров — в кеше лежат
только агрегаты; это работа для трека данных, не фронтенда.

**6. Мой список.** На пустом запросе поиск показывает отмеченное с фильтрами по регистрам,
и фильтры считаются по самому списку, а не по каталогу: «Расследование 18, Миф и обряд 15,
Телесное 7…». Там же вход в импорт (`/settings?import=1` открывает шторку сразу). Проверено:
40 строк → 18 после фильтра.

**7. Telegram по-родному — частично, и намеренно.** Добавлен тактильный отклик:
`tap` (действие), `pick` (перебор), `outcome` (итог) в `src/lib/telegram.ts`, вызовы — на
отметке просмотренного, старте, сохранении, отказе, переключении автора, фильтрах и чек-ине.
Вне Telegram это пустые вызовы, проверить их в браузере нельзя. Системная кнопка «назад» уже
была подключена в `AppShell`. **Палитру `themeParams` по-прежнему не подмешиваем** — это
правило дизайн-системы: от мессенджера берётся только `colorScheme`, цвета остаются наши.

## Трек А: тонкий бэкенд, который хранит факты (23.09)

Первый срез сделан и проверен целиком: отметка «смотрел» переживает перезагрузку.

**Что сервер делает и чего не делает.** Он хранит то, что человек сделал сам: просмотренное,
дневник, прогнозы, чек-ины, отклики на рекомендации и вердикты по автопривязкам. Подбор
по-прежнему считается на клиенте, каталог и разборы остаются общими данными. Это осознанная
граница первого среза: «пережить перезагрузку» — отдельная задача от «перенести модель».

**Где что лежит.** `worker/index.ts` — сам API (роутер руками, без фреймворка: десяток путей
не стоит зависимости), `worker/auth.ts` — проверка подписи Telegram и токены сессий,
`worker/schema.sql` — таблицы D1, `worker/env.ts` — минимальные типы платформы (полный пакет
типов Cloudflare тянет рантайм воркеров в проект, где основной tsconfig про браузер).
`wrangler.toml` держит конфигурацию; `npm run api` поднимает всё локально на 8787,
`npm run api:init` создаёт локальную базу, `npm run typecheck:worker` проверяет типы отдельно
от фронта.

**Вход.** Подпись `initData` проверяется на сервере и только там: HMAC-SHA256 по
отсортированным парам, сравнение за постоянное время, срок годности сутки. Токен бота — секрет
воркера, в клиент не попадает. Для разработки и проверок есть демо-вход, и разрешает его
сервер (`ALLOW_DEMO`), а не клиент: в боевом окружении переменная пуста, и такой вход просто не
работает. Сессия — 32 случайных байта в таблице, а не JWT: состояние всё равно в базе, и
подписанный токен пришлось бы отзывать той же таблицей.

**Клиент.** `src/api/store.ts` — один интерфейс с двумя режимами: без `VITE_API_URL` всё как
было (память вкладки, моки), с ним — сервер. Состояние приезжает одним запросом `/api/state`
при запуске, и пока оно едет, ни одна функция `api` не отвечает: `delay()` теперь ждёт
готовности. Иначе лента успевает посчитаться по пустому просмотренному, а потом дёргается.
Сервера нет или он молчит — приложение работает на моках: открываться без сети оно обязано.

**Что проверено** (локальный воркер + headless-браузер):
- отметили «Расёмон» просмотренным → полная перезагрузка → он в списке; сняли → перезагрузка →
  его нет;
- «в планы» из карточки долетело в таблицу `feedback` (`action=save`), прогноз — в `prediction`;
- запрос без токена получает 401, протухшая сессия молча меняется на новую;
- карточка, пришедшая с сервера неполной, больше не роняет экран: `asCard()` достраивает
  обязательные поля контракта. Нашлось это ровно так — заглушкой, положенной через curl, и
  белый экран был честным следствием.

**Чего ещё нет:** выноса справочников в R2 (эндпоинт есть, бакета нет — отвечает 404, и фронт
берёт запечённое), боевого развёртывания (нужен аккаунт Cloudflare: `wrangler d1 create`,
`wrangler secret put BOT_TOKEN`, `wrangler deploy`) и переноса дневника — статусы записей
по-прежнему собирает мок, сервер пока только записывает факты чек-инов.

## Механика под переключателем (21.09, решение владельца продукта)

Всё «наше» — операции мышления, продуктивное усилие, уровни и диапазоны, карта, «что
изменилось на карте», «кто чего хочет», фокус маршрута — **по умолчанию не показывается**.
Снаружи остаются кадр, объяснение словами («что это», «почему вам», «почему сейчас»),
разборы авторов и места разговора. Оценок Кинопоиска и «вердиктов» блогеров числом нет и
не будет — это тот же рейтинг в другой обёртке. Модель при этом работает как работала:
подбор, маршруты и чек-ин не меняются.

Как устроено: `src/lib/settingsStore.ts` — общий кэш настроек (`loadSettings` при старте в
`App`, `saveSettings` из экрана настроек, `useSettings` / `useMechanics`). Переключатель —
`UserSettings.showDetails`, в настройках называется «Показывать механику». Компоненты
механики (`OperationChip`, `OperationGlyph`, `StretchIndicator`, `StateChangeNote`,
`UncertaintyMark`, `CognitiveMap`) при выключенной механике **сами возвращают null** — экраны
о них не думают; текстовые следы (подписи «вводит / закрепляет», «фокус: …», строка «карта
уточнилась» в дневнике, разделы «Что делает» и «Кто чего хочет») закрыты в экранах через

механике), `/map` и `/onboarding/map` по прямой ссылке показывают `MechanicsOff`; после
диагностики без механики — сразу на «Сегодня», итог контрольной точки — словами.

Разборы и места разговора — на кадре: `Recommendation.analyses` / `.discussions` (сервер
прикладывает 2 разбора и 1 место; спойлер-правила те же, что на странице произведения), на

API — **500 запросов в день**, и его легко выбрать (21.09 выбран за час тестов), поэтому:
дневник на лету **не обогащается** (98 записей × 2 запроса), слейт и страница произведения —

по-русски, кинотеатры RU) → TMDb (кадр без надписей, overview, watch providers RU — данные

## Вход и диагностика (21.09)

Страницы `ScenarioFlow` в этой папке нет — экраны собраны по роутам §17 и контракту
`AssessmentSession`; при сверке с витриной править экраны и раздел «Экраны входа» в `app.css`.

- **`/welcome`** — что это за приложение, «Начать» → `/onboarding`, «У меня уже есть карта» →
  `/today`. Карта и три кадра — образцы, подписаны как образцы; берутся из `getMap` и
  `getSlate`, потому что отдельного эндпоинта под витрину в §17 нет. Без них экран живёт.
- **`/onboarding`** — быстрый старт или полная диагностика; `startAssessment(mode)` создаёт
  сессию, экран уходит на `/assessment/:id`. Минуты в описании режимов — текст, не данные.
- **`/assessment/:id`** — `AssessmentItem` с `AssessmentProgress` над ним, «Дальше» закрыта,
  пока нет ответа; «Пропустить» шлёт `null`; «Пауза» — `pauseAssessment` и выход на
  `/onboarding`. Ответ типизирован: `AssessmentAnswer` в `tmdf.ts` (по варианту на каждый
  `AssessmentResponse`), `answerAssessment` принимает `AssessmentAnswer | null`. Задание
  сменилось — компонент перемонтируется по `key={item.id}`, черновик не тянется. Сессия
  `completed` → `completeAssessment` → `/onboarding/map`.
- **`/onboarding/map`** — первая карта, слова о грубости оценки, предложенный фокус
  (`suggestedTargets`, только показ — выбор на `/map`), выход к «Сегодня».
- **`/checkpoint/:id`** — тот же `AssessmentScreen` с `checkpoint`: если `researchConsent`
  выключен — сначала `ConsentCard` (`updateSettings({ researchConsent: true })`, «Не сейчас»
  → `/today`), затем задания, в конце — `StateChangeNote` по последней точке истории карты:
  операции, у которых уровень или диапазон отличаются от предыдущей точки; если таких нет —
  «карта не сдвинулась». Проверено с выключенным согласием на временно правленом моке.

Сверх §17 в слое данных: `getAssessment(id)` (экран открывается по прямой ссылке и после
паузы) и `pauseAssessment(id)` (пауза на сервере — сессия переживает закрытие мини-приложения).
Своего эндпоинта у контрольной точки нет: кто её назначает и как участник на неё попадает
(уведомление бота, кадр на «Сегодня») — вопрос к серверу; в моке заведена `cp-1`. Мок
диагностики держит ход сессии в памяти: пять заданий подряд (все шесть видов ответа), потом
`completed`. Тестового раннера нет; прокликано по CDP: оба потока до конца, пауза, пропуск,
согласие (кнопка закрыта до галочки).

## Импорт истории (21.09)

`src/lib/import`: `parseCsv` (RFC 4180), `detectFormat` по заголовку, парсеры четырёх форматов
→ `ImportedRecord` (оценка нормализована к 0–10, но в интерфейс не попадает), `toJourneyEntries`
сопоставляет с каталогом: сначала по IMDb/ISBN из `externalIds`, потом по названию (регистр,
диакритика, артикли сняты) и году ±1. Несопоставленное возвращается отдельно — это материал для
сетки знакомства; сериалы (`type: 'series'`) откладываются в `skipped` — в контракте их пока нет.
Проверено на образцах трёх форматов и на двух реальных файлах конвертера с Кинопоиска
(21.09): **импорт-формат Letterboxd** (`Title,Year,Rating10,WatchedDate,tmdbID,imdbID`;
88 фильмов, у всех есть IMDb или TMDb ID, у 5 нет латинского названия) и **текстовый список
«не найдено»** (`## Название` + «Ключ: значение»; 12 сериалов с ID Кинопоиска, у 6 без названия).
Оба формата — `letterboxd_import` и `kinopoisk` в `formats.ts`. Записи без названия держатся
за ID: TMDb/IMDb резолвит их напрямую, ID Кинопоиска — через Wikidata (свойство P2603), без
обращения к самому Кинопоиску. Тестового раннера в проекте по-прежнему нет. Профили Кинопоиска
не парсим: условия сервиса и чужие данные; путь — согласие и собственный экспорт участника.

**Сохранённая страница «Оценки» профиля Кинопоиска** (21.09, `parseKinopoiskHtml`) — сам
источник, без конвертера: участник открывает свои оценки и делает «Сохранить как» на каждой
странице (по 50 записей). Разбор регулярками по `div.item`: ссылка `/film/ID/` или
`/series/ID/`, русское название с годом в скобках («(сериал, 2017 – 2020)», «(мини-сериал,
2017)» → `series`), оригинал из `.nameEng`, дата `дд.мм.гггг` → ISO, оценка из
`ur_data.push({film, rating})` (запасной путь — `div.myVote`), сущности `&nbsp;` и т. п.
раскрываются. Определение — по `profileFilmsList` / `ur_data.push(`, проверяется до CSV.
Проверено на двух реальных страницах: 100 записей, 88 фильмов + 12 сериалов, у всех ID,
год, оценка и дата; сходится с блоком «Оценки в цифрах» профиля с точностью до третьей,
не присланной страницы. **В такой странице лежат сессионные токены (`xsrftoken`,
`user_code`)** — парсер их не читает, в `ImportedRecord` они не попадают; сырой файл нельзя
ни хранить, ни отправлять на сервер: разбор только на клиенте.

Несколько файлов за раз — `parseExports(texts[])`: записи склеиваются, повторы убираются
по любому совпавшему признаку (ID Кинопоиска / IMDb / TMDb / ISBN, «название + год» и
«оригинал + год», чтобы CSV конвертера с английскими названиями и страница с русскими
не задваивались); первый файл выигрывает. Не склеиваются только безымянные строки
конвертера с одним лишь TMDb/IMDb-ID — их схлопнет `toJourneyEntries` по `work.id` после
сопоставления. `api.importHistory` принимает `string | string[]` и возвращает `sources[]`.

Проверка экранов: `--dump-dom` для статики и CDP-раннер (`Runtime.evaluate` по голому WebSocket
Node 22) для прокликивания потоков — headless Chrome этой версии не выходит сам после dump,
его надо убивать.


## Боевой запуск на bothost.ru: профили и холодный старт (23.09)

Приложение живёт на **https://recomend.bothost.tech** (bothost, бот «Transformative Media»,
тариф Pro). Cloudflare не понадобился: тот же воркер крутится под Node.

**Сборка.** `npm run build:bothost` (`tools/build-bothost.mjs`) кладёт в `deploy/bothost/` и
`deploy/tm-bothost.zip`: фронт с `VITE_API_URL=/` (API на том же адресе), `worker.cjs` —
`worker/index.ts`, собранный esbuild под Node, `server/index.js` (статика со сжатием, `/api/*`,
прокси `/kp-api` с ключом из окружения), `server/d1-sqljs.js` — D1 поверх SQLite в памяти
(sql.js, WebAssembly: на хостинге нечего компилировать) со сбросом в `DATA_DIR/tm.sqlite`
(`/app/data` переживает обновления), `seed/owner.json`. Обновление — «Архив → Залить новый
архив» в панели бота; токен, переменные, домен и база остаются.

**Профили.** Вход по подписи `initData` (токен бота bothost задаёт сам в `BOT_TOKEN`). Вне
Telegram — гостевой профиль, свой на каждый браузер (`u-anon-…`, токен в localStorage), а не
общий демо: иначе гости портили бы подбор друг другу. `ALLOW_DEMO=0` его закрывает.

**Владелец.** `OWNER_USERNAME` (по умолчанию `Tacticheskiy_Enot`): при первом входе его
пустой профиль получает историю из `seed/owner.json` — дневник (93 записи, 91 после дублей
id), 88 оценок, 79 фильмов присланного списка (`tools/bothost-seed.ts` собирает его из
`userHistory`, `userRatings`, `userWatched`). Один раз: дальше это обычные записи.

**Клиент в режиме сервера** больше не подкладывает всем историю владельца: `baseJournal()`,
`baseWatched()`, `ratingOf()` берут моки только без сервера (разработка, standalone). С
сервером история — из `/api/state` (`journal`, `ratings`, `watched`, `profile`).

**Холодный старт.** Пока размеченного досмотренного меньше `MIN_RATED` (10), `getSlate`
отдаёт пустой слейт с `coldStart: { rated, needed }`, и лента объясняет, что сначала нужны
оценки, — вместо моков сценария. Экран `/rate` (`RateScreen`): 37 известных размеченных
фильмов (`src/mocks/ratingDeck.ts`, отбор и порядок — там), шкала словами «Мимо / Слабо /
Нормально / Хорошо / Отлично» (1–5), «Не смотрел» прячет строку. Оценка → таблица `rating`
(`PUT /api/rating/:id`) → запись «досмотрено» в истории с весом → подбор. Оценённое уходит из
ленты как виденное.

Проверено (сервер локально, подписи `initData` поддельным токеном, Playwright 390×844):
владелец — 88 в архиве, 79 в списке, лента из 6; повторный вход историю не дублирует;
перезапуск сервера всё сохраняет; чужая подпись — 401; новый участник — объяснение и
«Оценено 0 из 10»; гость оценил 10 → лента из 6 и переживает перезагрузку.

## Telegram: высота оболочки и вход с нескольких аккаунтов (24.09)

- **Высота.** Оболочка в Telegram — `position: fixed; inset: 0`, а не `height` по
  `viewportStableHeight` (на Android до раскрытия ≈100 px) и не `100%` (во WebView Android у
  html/body бывает нулевая высота, пока окно раскрывается). Симптом был: лента сжата до полоски,
  у нового участника — только навигация сверху. Проверено Playwright с `html,body{height:0}`.
- **Токен сессии** в localStorage — по ключу `tm.token.tg<id>` (вне Telegram `tm.token.guest`):
  хранилище WebView общее для всех аккаунтов Telegram на устройстве, и второй аккаунт входил
  под первым. Старый общий ключ `tm.token` удаляется при чтении.

## Трек Б: петля прогноза (24.09)

- **Что пишется.** `prediction` (+ колонка `model_p` — вероятности модели), `checkin` (факт,
  причина, время), `journal.started_at` (для «дней до броска»), `feedback` (начать / в планы /
  не сейчас + причина) и новая `impression` — какие кадры показаны, на каком месте, в какой
  ленте. У слейта теперь уникальный id (`s-<усилие>-<время>`), показы уходят одним запросом
  после отрисовки ленты и не держат её, если сервер молчит.
- **Миграции** — `worker/migrate.ts`: новые колонки в старые таблицы (SQLite не умеет
  `ADD COLUMN IF NOT EXISTS`), один раз на процесс, по `PRAGMA table_info`. Проверено на базе
  со старой схемой: колонка добавилась, `impression` создалась, данные на месте.
- **Модель вероятностями** — `difficultyOdds` в `src/lib/model/recommend.ts`: упорядоченная
  логистика по разрыву «уровень фильма − (комфорт + шаг усилия)», крутизна `DIFFICULTY_SPREAD`
  = 0.6 (прикидка, подгоняется в Б5). Точечный прогноз (`expectedDifficulty`) не менялся.
- **Отчёт** — `worker/loop.ts` (`loopReport` над строками, `loopRows` из базы): Брайер и
  попадания модели, человека, «всегда в самый раз» и частоты фактов; таблицы «прогноз против
  факта»; согласие человека и модели; броски по причинам и медиана дней; показы → начали /
  в планы / не сейчас. «Частота фактов» считается по тем же наблюдениям — это оптимистичная
  база, на малых N она бьёт всех; честное сравнение — после 30+.
  Входы: `GET /api/report/loop[?scope=me]`, экран `/loop` (в настройках у владельца),
  `npx tsx tools/loop-report.mts ~/Downloads/tm.sqlite [--user u-…] [--json]` — базу
  скачать из файлового менеджера bothost (`/app/data/tm.sqlite`).
- **Б3.** `startWork` пишет запись в дневник всегда (раньше — только при прогнозе человека) и
  кладёт её в историю сразу; лента после «Начать» перечитывается, и фильм встаёт первым
  («Сейчас», «Закончил / Бросаю»).
- **Починено:** `checkIn` брал запись из моков сценария и отправлял на сервер чужой `workId`;
  теперь — настоящая запись, её статус и дата обновляются на месте, «что дальше» после
  чек-ина — из настоящего подбора, а не книга из сценария.
- Проверено сквозным прогоном (Playwright, локальный сервер): владелец → «Начать» с прогнозом
  «в самый раз» → фильм первым в ленте → чек-ин «досмотрел, тяжело» → отчёт: 1 наблюдение,
  Брайер модели 1.318 против 2 у человека и «всегда в самый раз», 6 показов, 1 старт (17%).
  Экран `/loop` и CLI дают те же числа. Регрессии (гость, два аккаунта, поиск, произведение,
  экран сети) — чисто.

## Ручная разметка «ролик → фильм» и сторож на повседневные названия (26.09)

**Предмет канала.** У `VoiceSource` появилось `medium?: 'film' | 'book'` рядом с `tier`. Денис
Чужой и bookspace обозревают книги (поправка владельца 26.09), туда же четыре книжных канала
из списка 22.09. Ярус обзорщика имеет смысл только внутри своего предмета: книжный обзорщик
ничего не говорит о том, посмотрели фильм или нет, — поэтому в ось массового внимания к фильму
идут только `medium: 'film'`. Предмет и ярус лежат рядом с каналом в `.cache/youtube/channels.json`
(`tools/_chmap.mts`): у материала есть только название канала, а на YouTube оно другое, чем в
списке владельца, — «TerlKabot channel» против «TerlKabot».

**Третья ось массовости.** `tools/overlooked.mts` считает массу как наибольшее из трёх мест:
зрители Trakt, просмотры русской статьи, обзорщики. Обзорщики — единственная мера, снятая с
русскоязычной публики: «Чебурашка» и «Не время умирать» по Trakt выглядят обделёнными, а их
брали BadComedian и КИНОКРИТИКА. Ось работает только вверх: «обзорщик взял» — свидетельство
массового внимания, «не взял» — свидетельство ничего, обзорных каналов у нас восемь. Заодно
разошлись «разборы» и «обзоры»: 98 фильмов, у которых был только массовый обзор или только
книжный канал, честно перешли в «без разбора» (407 против 331).

**Таблица разметки.** `deploy/markup-xlsx.command` → `.cache/markup/film_reviews.xlsx`:
4 940 роликов кино-каналов от пяти минут на двух листах — «Обзоры» (3 398) и «Эссе» (1 542),
врозь по просьбе владельца: у обзорщика фильм почти всегда в заголовке, у эссеиста заголовок
бывает про что угодно, и это разная по скорости работа. Третий лист, «Без разбора», — взгляд
со стороны фильма: 989 наших фильмов, о которых не высказался ни один обзорщик и ни один
эссеист, сверху те, кого чаще называют в постах; там же колонка «Знаю разбор — ссылка», и
импортёр читает её наравне с выбором из списка. Колонка «Фильм» — выпадающий список из 1 629
значений на скрытом листе «Справочник» (именованный диапазон `film_list`, рядом ключ `tmdb:`).
679 строк заполнены догадкой сопоставителя: человеку остаётся подтвердить или поправить, а не
искать фильм в списке из полутора тысяч. Первое значение списка — «— не про фильм —»: у Клима
Жукова и КИНОКРИТИКИ таких роликов сотни. Список предупреждает, а не запрещает — фильм, которого
у нас нет, можно вписать руками, и это очередь на добавление. Собирают файл два шага:
`tools/markup-xlsx.mts` (данные) и `tools/markup-xlsx.py` (сам xlsx, нужен openpyxl — ставится
в `.cache/venv` первым запуском команды). CSV не подошёл: выпадающего списка он не умеет.

**Разметка обратно.** `tools/import-markup.py` читает заполненный файл (`--in`) или живую
Google-таблицу (`--url`, нужен доступ «по ссылке»; качает `curl`, а не питон: у свежей сборки
python.org нет корневых сертификатов, и `urllib` падает на сертификате Google) и складывает решения в
`tools/markup-verdicts.json`. Решением человека считается не всякая заполненная ячейка: 679
строк отдаются уже заполненными, и принять их за разметку значит записать догадку в правду.
Решение — это «Проверено» = «да» либо значение, отличное от догадки. Ключ берётся со скрытого
листа того же файла, а не из моков: файл мог быть собран неделю назад.
`tools/build-essay-index.mts` кладёт вердикты поверх догадок — привязывает то, чего регексп не
увидел, снимает лишнее и не перепроверяет человека сторожами (`evidence: 'human'`).
Перегенерация индекса разметку не стирает.

**Сторож на повседневные названия.** `tools/build-ordinary.mts` → `.cache/ordinary.json`,
читают оба генератора и передают в `nameMatch` (`MatchOptions.ordinary`). Правило: где выделение
и так требуется (посты), капса мало — нужны кавычки; и всегда — точная форма, без склонения.
Два признака подряд, оба по корпусу, списка руками нет. Первый (все слова названия —
повседневные) сам по себе врёт: основа в пять букв слепляет «сталкер» со «сталкивается»,
«престиж» с «преступлением», и в ловушки попадают «Сталкер», «Прибытие», «Престиж» — то есть
комментарий в `ordinary-names.mts` про замер 24.09 не подтвердился. Решает второй признак —
встречается ли строчными сама фраза: «один дома» и «назад в будущее» собраны из обычных слов,
но как фраза в речи не звучат. На 65 949 постах: 380 названий по словам → **36** после проверки
фразой. Замер эффекта (26.09): в постах снято 20 привязок, 17 из них ложные («ВСЕМ СПАСИБО»,
«Детектива Пикачу», «ЗОЛОТОЙ МАЛЬЧИК», «Миссия: невыполнима», «в «Октябре»» — это кинотеатр),
потеряны два проходных упоминания; в роликах снята 31 привязка, все ложные, ни одной новой
(«СЛОВО ПАЦАНА» → «Пацаны», «Звёздные войны» → «Звёзды», «Голос Улиц» → «Голоса»).
Итог: посты 1 365 → 1 352, ролики 758 → 727.

**Заявки участников.** Таблица `suggestion` в D1 (`kind` = `work` | `voice`), `POST /api/suggestion`,
очередь владельцу — `GET /api/admin/suggestions` по `TM_ADMIN_TOKEN` и `tools/suggestions.mts`.
Входы: «Нет нужного фильма?» под результатами поиска (запрос уходит с заявкой) и «Знаете разбор,
которого здесь нет?» в блоке «Кто разбирал» (с названием фильма). В каталог заявка сама не

видом человеческого решения. Нет снимка — засчитывается только «Проверено» = «да».

вкладку надо закрыть и открыть ссылку заново.

## Свайп вправо — кто разбирал (28.09, решение владельца)

## Контрольные замеры сборщика (29.09)

За день нашлось четыре тихие потери: импорт таблицы читал одну ссылку из восьми, ручные
привязки к роликам чужих каналов выбрасывались, у 940 смотренных не было данных о внимании,
Wikidata отвечала 429 — и ни один шаг не падал, просто число на выходе становилось меньше.
Теперь такие числа сравниваются с прошлым прогоном каждое утро.

- **Что меряется** — `tools/collect-metrics.mts`, двадцать чисел, только из файлов, без сети:
  выемка Telegram (постов, каналов), индекс разборов (фильмов с материалом, материалов, доля
  «не проверено» — как в `voices-report`), ролики (`essaysAuto`: привязок, каналов, ручных
  `evidence: human`), посты (`postsAuto`: привязок, каналов), карточек Wikidata, соупоминания
  (`comentions`, `.cache/mentions.json`), кандидаты в источники, решений в
  `markup-verdicts.json` и **ручных привязок мимо индекса** (слово человека есть, ролика в
  `essaysAuto`/`essays.ts` нет), внимание (Википедия, Trakt, смотренных владельцем без данных —
  `seeds/` не читаются), роликов в `.cache/youtube/videos.json`. Последние три группы — не
  выходы сборщика, а его входы (import-markup, build-attention, youtube-dump), но терялось
  именно там. Отдельно по каналам — привязки роликов и постов, посты в выемке.
- **Где лежит** — история `.cache/collect-metrics.json`: снимок на день (повторный прогон в тот
  же день заменяет утренний), последние 30. Первый снимок — 29.09 вечером, пока
  `build-attention` ещё дописывал `attention.json`: рост внимания на следующее утро — это он.
- **В сборщике** — шаг 4б `collect.mts`, после всех индексов и до публикации: таблица и
  предупреждения попадают в `.cache/collect/<время>.log` раньше строки о публикации, итог —
  строкой «ВНИМАНИЕ: контрольные замеры — N предупр.». Публикацию не держит.
- **Как читать.** Таблица «было → стало» против прошлого снимка, `!` в начале строки — число
  под подозрением; всё на месте — «без изменений». Предупреждения: счётчик упал больше чем на
  10%; упал до нуля (так выглядит 429 от Wikidata — `filmBaseWiki` пустой); доля «не проверено»
  выросла больше чем на 5 пунктов; «мимо индекса» и «смотренных без внимания» выросли больше
  чем на 10% (и не меньше чем на 5); канал пропал целиком (было ≥ 3) или сдулся вдвое (было
  ≥ 20); файл не читается — у числа «—» и строка «нет данных» (например, `attention.json`,
  пойманный на полуслове). Рост предупреждением не считается.
- **Запуск руками** — `npx tsx tools/collect-metrics.mts` (`--dry` — не сохранять, `--strict` —
  код 1 при предупреждениях). Проверить сам замер: `--src essaysAuto=<урезанная копия>` (имена —
  в `SRC` в начале файла); с подменой снимок в историю не пишется. Так проверено 29.09: без
  «ЭПИЗОДОВ» и трети роликов, с пустым `filmBaseWiki`, восьмой частью решений и выемкой без
  канала — восемь предупреждений, все по делу; повторный прогон на настоящих — «без изменений».
- **Отправная точка 29.09:** 1 443 фильма с материалом, 3 780 материалов, «не проверено» 58,8%;
  ручных привязок мимо индекса — **293**: 290 из них с листа «Без разбора» (роликов нет в
  дампе), то есть это ровно потеря, починенная сегодня в `build-essay-index`: лежащий
  `essaysAuto` (17:39) их ещё не содержит. После ночного прогона число должно упасть до единиц;
  если не упало — чинилось не до конца.

  потом `youtubeNet.down = true`: оставшиеся ролики остаются без названия, канала и
  длительности, oEmbed по ним не спрашивается (иначе каждый ждал бы свои 10 с). В лог — строка
  «ВНИМАНИЕ: YouTube не отвечает (<код>) — N роликов остаются без…». HTTP-ошибки (403 квоты и
  т. п.) обрабатываются как раньше — пропуск пачки.
- **Цена дня без YouTube.** Название ролика берётся из поста, автор — из пересылки или канала,
  шортсы не отсеиваются (длительность неизвестна). Индекс постов собирается заново каждый
  прогон, так что следующий прогон с сетью всё исправит сам.
- **Проверено** подменой `fetch` на отказ: 120 роликов — два обращения к сети, 5 с, ни одного
  исключения; `tsc --strict` по `youtube.mts` чистый. Боевая проверка — прогон 30.09.
- `build-essay-index` по-прежнему бросает на сетевой ошибке, но шаг необязательный: остаётся
  вчерашний `essaysAuto`. Запасной источник метаданных — дамп `.cache/youtube/videos.json` —
  в бэклоге (`BACKLOG.md`, OPS-8).

## Сторожа тёзок: «Легенда» 1985-го и другие (30.09)

К «Легенде» Ридли Скотта прилипло восемь чужих материалов: «Я — легенда», две экранизации
«Legend of Zelda», «Брюс Ли — воин, актёр, легенда», дважды «Легенда №17», «Легенда» Хелгеленда
и обзор 2015 года. Причины разные, и чинились они общими правилами, а не списком исключений:

- **Номер — продолжение названия** (`title-match.mts`): «Легенда №17» — как «Джокер 2», и в
  кавычках тоже: внутри «…» после нашего названия не должно быть ни буквы, ни цифры, ни №.
- **Латиница продолжается латиницей** (`latinContinues`): «Legend of Zelda», «The Dark Knight
  Returns», «Kingdom Come Deliverance», «Superman: Red Son» — не наше оригинальное название.
  Следующее слово учитывается в том же регистре: «I SEE YOU Official Trailer» — подпись, не
  продолжение. То же правило стоит в улике `original` (`evidence.mts`): раньше обе «Зельды» шли
  с уликой, то есть как проверенные.
- **Капс в заголовке капсом ничего не выделяет** (`shouting`) — для повседневных названий:
  «БРЮС ЛИ - ВОИН, АКТЕР, ЛЕГЕНДА!», «У МЕНЯ ДЕНЬ РОЖДЕНИЯ!», «…И ДРУГИЕ».
- **Сторож «Я — легенда»** в `RIVALS` — тот же приём, что «Человек-легенда».
- **Чужой режиссёр после названия в кавычках** (`foreignCreator`, противоречие `conflict`):
  «Легенда» (18+) Брайана Хелгеленда, «Дракула» Люка Бессона, «Начало» Деа Кулумбегашвили,
  «Королевство» Ларса фон Триера. Только родительный падеж (именительный — подлежащее, часто
  актёр: «…таланта» Николас Кейдж дал…) и только если создатели у нас записаны кириллицей;
  год фильма рядом (улика `year`) проверяется раньше и побеждает.

**Замер на индексе ночного прогона 30.09** (скрипты сравнивают старую и новую версию правил на
текущих привязках): по заголовку снимается 27 автопривязок из 2 654, вердикт меняется у 24 из
3 142 — улика `original` уходит у 10 (все внутри чужих латинских названий), противоречие
режиссёра — 14 (все тёзки и ремейки). Ложных снятий в выборке не нашлось; единственное —
«I SEE YOU Official Trailer» — поймано на первом круге и исправлено правилом регистра.
Ручные решения (`evidence: human`) сторожа не трогают. В индексы изменения попадут со
следующим ночным прогоном.

**Что не закрыто:** обзор «"Легенда" — обзор фильма» 2015 года (тёзка по времени, режиссёр не
назван) остаётся; «Пацаны» 1983-го собирают около 25 материалов о сериале The Boys и «Реальных
пацанах»; «ДРАКУЛА Бессона» — режиссёр без кавычек; создатели латиницей не сравниваются. Всё
это — OPS-9 и OPS-10 в `BACKLOG.md`.

## Запасные данные о роликах: кэш ответов YouTube (30.09)

Продолжение «Сборщик не падает от сбоя YouTube». В день без YouTube `build-telegram-index`
раньше оставлял ролики без названия и длительности, и шортсы проходили в индекс. Теперь:

- `videosApi` после каждого удачного запроса дописывает ответы в `.cache/youtube/meta.json`
  (название, канал, длительность, дата). Когда сеть легла (`youtubeNet.down`), недостающее
  берётся оттуда, потом из дампа `.cache/youtube/videos.json`; в лог — «из кэша и дампа: N из M».
  Дамп сам по себе почти не помогает — из 88 роликов по ссылкам из постов в нём 4, — поэтому
  главный источник кэш. Он пустой до первого прогона с сетью: наполнит ночной прогон 01.10.
- `build-essay-index` на сетевой ошибке выходит с кодом 3 и строкой «ВНИМАНИЕ: YouTube не
  отвечает — индекс роликов не пересобран, остаётся прежний essaysAuto», ничего не записав.
  Нарочно не продолжаем: частичный обход записал бы индекс без половины каналов и 293 ручных
  привязок, а вчерашний полон. Шаг в сборщике необязательный, прогон идёт дальше.
- Проверено подменой `fetch`: день с сетью пишет кэш, день без сети отдаёт ролик из кэша и
  ролик из дампа, неизвестный остаётся без данных.
